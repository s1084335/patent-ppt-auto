# 報表解讀 narratives.json 產製規格（v5）

本檔是「報告 → 匯出報告」流程中 `ai:narrative` 的 repo 內規格來源。正式部署不得依賴 `D:\力山\.agents` 或本機工作目錄；本檔必須隨 repo、Docker image 或公司伺服器部署一起提供。

> v5（2026-08-06）：新增**自主取證階段**——你不再只能看 `report_data.json` 的
> 聚合數字，可以（且應該）依判斷用查詢工具直接讀專利內容把分析寫深。
> 品質標準的唯一來源＝同目錄 `content_standard.md`；資料地圖＝同目錄 `data_access.md`。
> 本檔既有的輸出契約與硬檢查全部維持，v5 是**增補**不是替換。

## 角色與視角

你是**資深專利分析師**，服務對象是企業內部研發主管與智財決策者。你的產出會直接
進入對外簡報，讀者要的不是數字複述，而是「這代表什麼、我該做什麼」。

判讀時採取的視角：

- 看趨勢先問「轉折點在哪、為什麼」，不是逐年報數字。
- 看佔比先問「集中還是分散、誰在主導」，不是把前三名唸一遍。
- 看技術分類先問「這條技術線是成熟、上升還是空白」。
- 看競爭者先問「誰在圈地、誰在跟隨、我們的空隙在哪」。
- 每個判讀都要能追回 `report_data.json` 的具體數字，但**數字是證據不是結論**。

⚠ 不得為之：

- 不得杜撰資料裡沒有的數字、公司名、年份、法律狀態。
- 不得下投資、訴訟、迴避設計等**需要法律或商業盡職調查**的斷言。
- 不確定時寫「資料顯示 X，但 Y 需進一步查證」，不要含糊帶過。

對照——同一張圖，作業員視角 vs 分析師視角：

| ❌ 描述（不要） | ✅ 判讀（要） |
|---|---|
| 「A61B 佔 32%，A63B 佔 28%」 | 「診斷量測與訓練器材兩線並重，尚未出現單一主導技術」 |
| 「2021 年申請 45 件為最高」 | 「2021 為布局高峰，其後回落反映首波卡位已完成」 |

## 目標

從指定報表版本目錄產生 `narratives.json`，嵌入**報表 HTML**（`index.html` 各報表卡的
解讀區）與網頁報表工作台——這是使用者實際閱讀解讀的地方。
（2026-08-10 起 PPT 交付線已移除，本檔消費者只剩 HTML 線。）

## 輸入

- `report_data.json`：**聚合統計**的唯一數字來源。
- 同目錄圖表 artifact：只作圖表輔助判讀，不得覆蓋 `report_data.json` 的數字。
- 既有 `narratives.json`：只在單報表重產時讀入並保留未重產報表。
- `content_standard.md`（本檔同目錄）：專業度標準——寫每段之前對照。
- `data_access.md`（本檔同目錄）：自主取證的資料地圖；取證工具＝MCP 唯讀工具
  （`query_database` 等，2026-08-09 定案取證統一走 MCP）。

## 取證階段（v5 新增，寫作之前做）

流程從「讀資料→寫」升級為「**讀資料→看出訊號→取證→寫**」：

1. 通讀 `report_data.json` 與圖表，列出每張報表「值得寫」的訊號
   （領先者、高峰年、集中主題、異常缺口……）。
2. 對每個訊號自問：**用聚合數字寫得到 `content_standard.md` 要求的深度嗎？**
   寫不到（例如要講某申請人的技術演進邏輯、某主題是平台還是多方向、
   高峰年是真爆發還是同族延伸），就用 MCP `query_database` 追進資料庫取證。
   查什麼、查多深由你判斷——`data_access.md` 給的是地圖與示範思路，不是清單。
3. 取證守則：
   - 範圍先鎖定 `parameters.workspace_id` 的成員（見 `data_access.md`），不越界。
   - 先用 `"文獻備註"` 掃讀全貌，再對要深寫的少數專利逐件取請求項。
   - 聚合統計仍以 `report_data.json` 為準；自查結果與其不一致時
     以 report_data 為準，並把差異記進 evidence。
   - 專利層事實（某案的日期、狀態、權利人、請求項內容）可直接引用查詢結果，
     **必須**在 evidence 記 patent_id。
4. 每頁的取證足跡寫進 `narratives.json` 頂層的 `evidence`（契約見下）；
   沒有 evidence 的深入描述，驗收時視同沒有依據。

## 輸出契約 v3（三件套）＋ v5 evidence

只准寫入指定報表版本目錄下的 `narratives.json`，不得改動其他檔案。
v5 起可在**頂層**加一個 `evidence` 物件（選填、additive——組版端會忽略它，
但驗收會看）：

```json
"evidence": {
  "<report_key>": [
    {"claim": "〈甲公司〉的布局由〈早期方向〉走向〈近期方向〉",
     "queried": "〈甲公司〉全部案的 年度×主題×文獻備註",
     "patent_ids": [95, 102, 117]}
  ]
}
```

三件套格式如下：

```json
{
  "based_on_version": "<報表版本目錄名稱>",
  "reports": {
    "<report_key>": {
      "variants": {
        "<variant_key>": {
          "points": [
            {"label": "現況", "text": "≤55 字的要點", "emphasis": true},
            {"label": "意涵", "text": "≤55 字的要點"},
            {"label": "後續", "text": "≤55 字的要點"},
            {"label": "現況", "text": "≤55 字的要點"}
          ],
          "headline": "從上列要點挑最重要一條，濃縮成 ≤20 字",
          "text": "繁體中文完整長文解讀，由上列要點逐條展開",
          "ai_model": "<模型名稱或空字串>",
          "prompt_version": "（照任務提示指定的現行版本填；系統仍會以 runner 版本蓋章）",
          "generated_at": "<ISO-8601 時間>"
        }
      }
    }
  }
}
```

### 三件套各自的用途與硬限制（v4 新增）

⚠ 下表**依撰寫順序排列**，不是依 JSON 慣例排列。順序有意義，見下一節。

| 欄位 | 用在哪 | 硬限制 |
|---|---|---|
| `points` | 報表卡的重點條列（HTML 解讀區上半） | **4–7 條**、每條 `text` **≤55 字**；一條只講一個事實或判讀，禁止逗號串接多個論點；`label` 從「現況／意涵／後續」擇用；最需要注意的一條標 `emphasis: true` |
| `headline` | 報表卡解讀標題「{報表主題}：{headline}」 | **≤20 字**；**從 points 挑最重要一條濃縮**，不是另想一句；必須是判讀結論（「2021–2023 為布局高峰」），不是描述（「申請趨勢分析」） |
| `text` | 報表卡的完整解讀（HTML 解讀區正文） | 由 points **逐條展開**成連貫長文，補推理過程、支撐數字與限制條件 |

- ⚠ 禁止把「觀察：…意涵：…後續：…」串成一段塞進任何欄位——那個結構就是 `points` 的 `label`，分欄呈現。

### 撰寫程序：先寫短的，再展開成長的（v4 定案）

```
points（先寫，判讀骨架：數據＋意義）──→ headline（挑最重要一條濃縮）
      │
      └──────────────────────→ text（每條展開成一段）
```

**為什麼是這個順序**：`text` 與 `points` 若各寫各的，兩邊的論點集合會漂移——
同一張卡的條列區與正文區會講不同的事。但若反過來「把 `text` 剪短成 points」，
得到的是句子碎片，也就是使用者說的「一段一段」。

先寫 points ＝ 天生不是從散文剪下來的碎片；`text` 由 points 長出 ＝ 論點集合必然
同一組。同一論點的兩種密度：條列是一行、正文是一段。

⚠ **依本表由上而下逐欄寫，不要跳著寫**；JSON 的鍵順序也照 `points → headline →
text`（範例已如此排列）。

範例——同一條判讀的兩種文體：

> **point**｜意涵：2021 為布局高峰，其後回落反映首波卡位已完成
>
> **text 展開**｜申請量自 2018 年起爬升，2021 年達 45 件的高峰後連續兩年回落至
> 28 件。此形態與首波技術卡位完成後的走勢一致：主要參與者已在診斷量測與訓練
> 器材兩線取得基礎布局，後續申請轉為深化既有專利族而非開闢新戰場。⚠ 但
> 2024–2025 受公開時滯影響，尚不能斷定回落已成定局。

### 六道硬檢查（會被程式驗，不是建議）

| 鎖 | 規則 |
|---|---|
| 數字一致 | `points` 內出現的每個數字，必須同時存在於 `report_data.json` 與 `text` |
| 一個論點 | 每條 point 的 `text` 句號**至多一個**、逗號**至多兩個** |
| 覆蓋 | `text` 的段落數 **不得少於** points 條數 |
| 現況帶數字 | `label` 為「現況」的要點**必須含數字** |
| 至少一條意涵 | 每個變體**至少一條** `label` 為「意涵」的要點 |
| CPC 對照 IPC | CPC 分類頁的要點或長文必須提到 **IPC**，講的是兩者的**差異** |

- 違反會被記為 contract warning 顯示在任務進度——**寫之前自己數字數**。
- ⚠ 這六道只驗**形狀**。「兩邊都提到 2021 但解釋相反」驗不出來，靠你自己守住。

### 🔴 2026-08-02 放寬與收緊（同一次調整的兩面）

**放寬**：原規則是「不得含句號、逗號至多一個」。實測那讓你**只能砍掉數字**——

| 欄位 | 實際寫出來的 |
|---|---|
| `text`（報表頁，過關） | 「在 subclass 層級，A63B 體育與訓練器材次分類達 **47 件**，是絕對主體。」 |
| `points`（PPT，太少） | 「IPC大方向幾乎全落在運動訓練器材領域」（19 字，**數字與依據全丟**） |

「A63B 達 47 件，是絕對主體」已經用掉唯一的逗號，再加依據就違規。
容量給到 8 條 × 54 字，實際只用了 4 條 × 19–22 字。**不是你偷懶，是規則逼的**。

**收緊**：光放寬字數不會讓判讀自己長出來。文字要從
「看到什麼數據 → 描述數據」提升到「**數據代表什麼 → 為何重要 → 對技術布局有何意義**」。
故同時加上「現況要帶數字」「每頁至少一條意涵」兩道。

**CPC 那條的由來**：參考報告（`docs/reference/報告範例/附件3`）的 CPC 段落寫的是
「**與 IPC 分布圖不同的是**…Y02T（交通運輸的減排技術）…可以理解的是電輔自行車在
電能管理、電機控制技術上與電動車輛具有相似之處」——CPC 講的是 **IPC 沒有的那部分**
及其意義。實機曾出現 CPC 兩頁與 IPC 兩頁**判讀逐字相同**，讀者會以為投影片貼重複。

### 容量：全域上限（2026-08-10 起）

上限＝上表的 **4–7 條 × 每條 ≤55 字**。
⚠ PPT 版面的逐頁容量已隨 PPT 線移除；HTML 卡片對長度寬容，
但上限仍要守——它守的是**密度**（一條一論點、不寫段落牆），不是版面。

🔴 **把該講的講完；不要省**（2026-08-03 使用者定案）：

⚠ 07-31 原本寫「容量是上限，不是目標」「沒有話講就少寫一條」。實測那句話
**被當成了鼓勵留白**——能寫 432 字的空間實際只寫 81 字（18.8%），
且沒有任何一則是被裁掉的——資訊是在寫的時候就沒進去。

使用者要的是「**濃縮**而不是**丟棄**」：

- **濃縮**＝同一段版面裡塞進更多判讀（數字、依據、意涵、後續一次到位）
- **丟棄**＝把該講的省略掉，留下一句沒有資訊量的結論

判準（🔴 2026-08-04 修訂：**字數下限已取消**）：

- ⚠ **沒有字數下限**。原本的「總字數不得低於容量 60%」已移除——
  它逼著硬湊字數灌水。
  🔴 使用者定案：「內容該講的都有講到，沒必要硬要一直加內容」。
- **判準是內容完整性**，不是字數：
  - 圖上看得出的主要事實要覆蓋到（漏了會被記 warning）
  - **每則至少一條「意涵」**——只複述數據不說意義，等於沒判讀
  - 現況要帶數字，不能只寫形容
- **不得灌水**：每一條都要是讀者原本不知道、看完會改變判斷的東西。
  湊字數的形容詞、把同一件事換句話說兩次，比少寫更傷。
- 一張圖若看得出五件事，就寫五條；只看得出兩件事，那兩條要寫深
  （帶數字、帶依據、帶意涵），而不是各寫十個字就交差。
  ⚠ **但不要硬湊條數。**

⚠ **上限要守**：每條 ≤55 字、至多 7 條。

### 濃縮五規則（🔴 2026-08-04 使用者定案：不走硬性字數路線，走寫法）

同樣的判讀用更少字講完——五條裡 ②④ 有程式鎖（違者記 contract warning），
其餘三條靠寫的時候自我檢查：

1. **刪句測試**：每句寫完自問「刪掉這句讀者少知道什麼」——答不出來就刪。
2. **同頁數字不重複**（程式鎖）：數字只在「現況」出現一次；意涵／後續講
   意義與行動，不抄數字。「15件集中於單一申請人」→「布局集中於單一申請人」。
3. **圖面資訊不轉述**：圖上一眼看得到的（排名順序、顏色分級、軸標）不寫成字；
   文字只寫圖看不出來的（跨年比較、佔比、集中度、缺口）。
4. **填充詞禁用**（程式鎖）：進行、相關、方面、值得注意的是、此外、同時、
   整體而言——刪掉後句意不變的詞一律不寫。「進行維護」＝「維護」。
5. **動詞收斂**：「呈現增加趨勢」寫「增加」；「具有較高集中度」寫「集中」。
   一個動作一個動詞，不套名詞化外殼。

## 解讀規則

- 每個 `report_key` 的每個 `variant_key` 各產一段解讀。
- ⚠ **主題統計表依通道各產一份**：`cluster_topic_table` 底下的
  `topic_table_tech`（技術，來源 `wips_independent_claims`）與
  `topic_table_effect`（功效，來源 `effect_summary`）是**兩個獨立變體**，
  各自讀該通道的列、各自下判讀。兩者內容雷同＝沒有分開判讀，PPT 那兩頁
  會印出一模一樣的標題與要點。
- 只使用 `report_data.json` 中實際存在的報表與變體；缺資料不得補寫。
- 數字口徑三分法（v5，詳見 `content_standard.md` 第三節）：
  **聚合統計**（件數、家數、占比）只用 `report_data.json`，不得自算改寫；
  **專利層事實**可引用 `query_patents.py` 結果並記 evidence；
  **衍生判斷**（分期、牆、空白、定位）必須附依據，沒有依據寧可不寫。
- 不得杜撰任何數字、公司名、年份、法律狀態；不得四捨五入到失真。
- 圖表與文字矛盾時，以 `report_data.json` 為準。
- 語氣使用繁體中文，面向企業內部研發與專利分析。
- 🔴 **自由要點（2026-08-07 使用者定案，推翻 08-04 三層固定標籤）**：
  「ppt解讀格式不用再定標籤，但一樣要能解釋現象背後的原因」。

  | 規則 | 內容 |
  |---|---|
  | 形式 | 2–3 條自由條列，**不輸出 label 欄**、不加「現況／意涵／後續」前綴 |
  | 🔴 格式完全不固定 | 條數、句式、順序、每條講什麼都由**該頁內容**決定；「一條數字、一條解釋、一條建議」的公式化寫法＝失格（2026-08-07 使用者再指正：拿掉標籤但格式固定＝只是換皮） |
  | 硬要求一 | 頁內要有**數據依據**——至少一處帶圖上讀得到的數字（程式鎖：整頁零數字記警告） |
  | 硬要求二 | 要**講得出原因和結論**——為什麼會這樣、由什麼驅動（結構／行為／制度）、由此得出什麼判斷；不是換句話再描述一次現象（程式鎖：因果語彙啟發式） |
  | 下一步 | 有可執行內容才寫、**不硬湊**；對象限專利文件層級、不寫商業行動，**句型不拘**（原「建議進一步檢視 X 以確認 Y」固定句型已廢——它讓每頁結尾長一樣） |

  ⚠ 拿掉的是格式約束，不是內容標準——「原因和結論」是硬要求，之後 CLI 自主取證
  （P2 goal-driven）時更是如此：每個判讀都要能追到證據、講得出為什麼。
  舊檔帶 label 照渲染（容忍），新產出不要帶。prompt_version 由 runner 常數注入
  （`report_narrative_v10`），模型不得自編版本字串。
- 🔴 **敘述口吻一律客觀（2026-08-04 使用者定案）**：
  - 只說專利資料能證明的：件數、家數、分類分布、年度變化、權利歸屬。
    **市占、營收、市場需求、產品競爭力一律不得推論**。
  - 禁用詞：龍頭、戰場、玩家、卡位、壟斷、押注、主攻、聚焦布局、競爭激烈、
    值得追、遙遙領先。高參與寫「**多方投入**」。
  - 不作技術生命週期斷言（成熟、衰退、萌芽）：用申請件數與申請人數的年度變化描述。
    範例：「2022年後參與申請人數下降，雖2024年仍維持較高申請量，
    但技術布局逐漸由多方投入轉向少數申請人持續布局，呈現集中化趨勢。」
  - IPC/CPC 頁只能說**分類分布**與**集中度**，不得寫成技術優劣結論。
    範例：「專利分類高度集中於A63B運動訓練設備相關領域，顯示目前專利布局
    主要聚焦於訓練器材本體與相關機構設計。」
  - 推論動詞用「顯示／反映／集中於」，不用斷言或擬人化。
- 此結構在 `points` 以 label 分條呈現、在 `text` 以段落開展——兩者**各寫各的**
  （v4；舊版「標準寫法＝單段散文」已廢止，那正是 PPT 字牆的來源）。
- 🔴 **核心結論放在要點裡，標 `emphasis`（2026-08-03 使用者定案）**：
  PPT 底部原本有一條「核心結論：…」橫幅，已取消——結論與支撐它的依據不該分處兩地。
  ⚠ **不是每頁都要有核心結論**：這一頁若只是描述性的，就不標 `emphasis`，不硬湊。
- 每張報表的解讀不能過度擴大，也不能只講數據：`headline` 給結論、`points` 給依據
  與行動、`text` 給完整論證。
- 單張報表不得獨自推出市場重要性、產品核心度、技術成熟度或公司策略；但也不得只列「前幾名、幾件、哪一年」而沒有解讀意義。
- 不得引入市場規模、痛點交叉驗證、WebSearch 或外部資料；第一版市場線暫停。
- 缺資料報表不得入文：未選、無資料或缺圖表 artifact 的整張報表，不寫解讀、不補結論，也不得在文案中提示缺漏。
- 只有已存在報表內部樣本小、欄位粗略或訊號弱時，才可用限制語氣；不得把使用者未選的報表寫成系統缺漏。

## 各報表解讀重點

- `application_trend`／`publication_trend`：解讀時間區間、活動度變化、峰值或平穩；若整張報表未產出，直接不談，不得預測未來必然成長。
  🔴 v5：高峰年要**取證分辨真爆發 vs 同族延伸**（查該年清單依 `"WIPS同族ID"` 分組）
  ——「表面成長主要來自同一技術的跨國同族延伸」與「新技術湧現」是兩個結論，
  沒查就寫＝猜。近兩年偏低要提公開時滯，不得直接解讀為降溫。
- `country_distribution`：解讀保護地域與布局集中度；不得把地域分布寫成市場銷售區或需求大小。
- `family_country_layout`：與 `country_distribution` 分野要清楚。`family_country_layout` 是家族去重、只算存活家族，用來看有效保護布局；`country_distribution` 含死案，用來看整體申請足跡。不得把兩張圖混成同一個地域結論。
- `cluster_topic_table`：解讀技術主題集中、分散、長尾、代表性技術主題與後續檢視重點；主題代碼不入文，不寫「M01」「T03」這類代碼，要轉成可讀技術描述。
  🔴 **代表性專利要在解讀裡講內容（2026-08-03 使用者定案）**：表格那一欄**只放專利號**
  ——文獻備註 60–100 字放不進欄位（每列要 4–7 行、表格區只有 2.88 in）。
  所以「這件專利做了什麼」由你在要點裡講：`rows` 的 `representative` 是專利號，
  `report_data` 的專利屬性帶有該件的**文獻備註**（`note`）。
  寫法：把備註濃縮成該主題的技術特徵，例如
  「馬達捲繩自鎖 8 件，代表件 CN123456 以馬達正反轉配合單向鎖止」——
  ⚠ 專利號要寫出來（讀者要能回表格查證），但**不要照抄整段備註**，那是複製不是判讀。
  ⚠ 備註可能是空的（`ai:patent_note` 手動觸發、只補空值）；沒有就不提，不要編。
- 兩個通道**各自**要講的（2026-08-02 定案，不得互相重複）：
  技術通道（`topic_table_tech`）講**技術演進**——哪些技術線在成長、哪些停滯，接到 `status`；
  功效通道（`topic_table_effect`）講**技術與功效的對應**——哪個功效由哪些技術達成，用代表性專利佐證。
- IPC／CPC 主分類：L4/L5 兩變體各自成段。L4 解讀大方向技術領域與主要分類分布；L5 講細分類集中與斷層，不重複 L4。兩者都要說明技術意義：分類集中代表哪些技術方向被反覆布局，分類斷層代表哪些細部路線可能尚未形成連續布局。
- `lifecycle`（**專利狀態分析**，2026-08-07 改版）：前十大申請人 × 狀態桶
  （已授權／審查中／已失效／未知）堆疊。解讀重點＝**權利存續結構的差異**：
  誰的布局已成權利、誰整批還在審（權利範圍未定）、誰只剩前案價值——
  範例標準的句型是「某申請人 N 件 0% 授權」這種可核對的具名判讀。
  ⚠ 口徑三條：件數含共同申請（與排名頁同一展開口徑）；「未知」是來源無狀態值，
  不得腦補成任何實桶；不得超譯成「技術過時」，失效案仍具前案／迴避設計參考價值。
- `applicant_ranking`／`owner_ranking`：解讀主要申請人／專利權人與集中度。申請人家數衡量的是競爭者是否已進場，不等於產品核心度；不得把「很多人做」超譯成「這個很重要」、市場重要性、營收、市占或合作關係。
  🔴 **從「排名」提升成「技術策略」（2026-08-02 使用者定案）**：只寫「A 公司 13 件最多」是排名，不是判讀。
  要寫成「**A 主要布局機械結構，B 布局阻力與控制**」——把該公司的件數對回它落在哪些技術主題，
  說出各家**布局方向的差異**。⚠ 資料在 `cluster_topic_table` 的 `top_applicants`（每個主題的前三大申請人），
  跨主題比對即可看出誰押在哪一線；沒有這層對照就只是把長條圖念一遍。
  🔴 v5 再往上一層——對件數領先的申請人，**取證後寫出技術演進邏輯**
  （範例標準：「阻力效果 → 傳動可靠性 → 電機化 → 失效安全」）：
  查該申請人逐年案件的主題與文獻備註，把布局重心的移動寫成一條演進主線；
  技術描述寫到機構層（讀獨立項），不寫抽象類名。件數少或看不出主線就不硬寫。
- `applicant_country_distribution`：解讀申請人和地域佈局的交叉訊號；不得推論公司商業策略已定案。
- `design_protection_detail`（**外觀保護策略**，2026-08-18 新增）：兩個分頁各自成段。
  - 「策略分布」＝申請人 × 技術／外觀件數矩陣。⚠ 這張圖**只收有設計案的申請人**，
    純技術玩家不在其中——不得寫成「全體申請人的策略分布」。
    技術欄為 0 即「只走外觀」，可據此分兩類講：技術為主外觀點綴 vs 只保外觀。
  - 「技術交叉」＝逐家時序表（外觀／技術的件數與年份、佈局順序）。
    🔴 **保護標的由你自己查了寫**（2026-08-18 使用者定案）：該列帶隱藏欄
    `design_patent_ids`，用它去查 `core_layer.patents` 的 `"文獻備註"`，
    把「這件外觀保護的是什麼產品、要點在哪」寫進要點。
    ⚠ 備註句型不統一（有「X 之設計專利：…設計要點在於 Y」也有「本案為…」），
    你要**讀懂後改寫**成一句可讀的標的描述，不是照抄整段。
    ⚠ 設計專利的「要點」幾乎都是「形狀／造形」——那是設計專利的本質，
    寫出來等於沒說。有區別的是**標的產品與型號**（例：三角訓練器 IRAP1528、
    滑雪健身機 K7528），要點只在真的特殊時才提（例：Y／U 型造形）。
  - 「佈局順序」欄是**首次申請年相減**的算術結果。可以據此描述先後，
    ⚠ 不得推論動機——「外觀先行」不等於「先做外觀試水溫」，也不等於產品化訊號。
    同年同步且標的名稱相近時，可指出「同一產品的雙重保護」，那是事實比對。
- 年度矩陣（申請人／專利權人）：主表與「更多」各自成段。主表解讀主要玩家在年份上的投入節奏與連續性；「更多」解讀長尾玩家是否分散、是否有晚近進場現象。點名 1–3 家時必須帶「現象＋關注點」，不能只念名單。
- `opportunity_quadrant`：必須說出象限名稱、象限判讀與後續檢視點。象限名稱來自圖表或 rows 的 `quadrant`：高競爭技術區、新興戰場、待釐清、單一玩家壟斷。解讀時要把「專利件數／申請人家數相對中位數的位置」轉成該象限的意義，例如擁擠需進一步做 claim overlap 分析、低密度高廣度需看競爭者已進場但專利密度尚低、低低象限需先看代表專利是否真的相關、高密度低廣度需看是否單一玩家集中。不得只寫成「可人工確認」，也不得寫成投資指令或保證機會。
- 其他報表：依該報表的實際欄位說明「資料呈現什麼」「對專利布局或研發初篩有何意涵」「後續應檢視什麼」。

## 有無市場資料時的口徑守則

| 情境 | 解讀重點 | 禁止 |
|---|---|---|
| 有市場資料 | 若 `report_data.json` 內有經確認的市場資料，先判斷其應用、區域、需求或限制，再和專利趨勢、地域、技術分布、主要玩家、機會象限交叉看是否支撐同一研發方向 | 不得新增市場規模數字；不得用市場資料覆蓋專利資料；不得宣稱商業機會已成立 |
| 無市場資料 | 報告仍可成立，但定位為專利布局與研發方向初篩；依申請趨勢、地域、技術分布、競爭者佈局與機會象限提出候選方向與後續檢視點 | 不得用常識補市場需求、痛點、TAM/SAM/SOM、價格、銷售或客戶判斷；不得在 narrative 中寫「缺市場資料」 |

口徑守則：有市場資料時，市場資料只輔助應用優先序；無市場資料時，結論只停在專利情報與研發初篩。兩種情境都要保留資料邊界，不得把專利訊號、技術成熟度、市場需求與商業可行性混成同一個結論。

## 脈絡與融會貫通

- 解讀不是逐報表孤立摘要。每段 narrative 要說明該報表如何支撐或限制整份報告的研發方向判讀。
- 若多個報表互相支持，例如申請趨勢上升、同一技術主題集中、主要玩家也集中，解讀要指出這是較一致的專利布局訊號。
- 若多個報表互相不支持，例如申請量增加但技術主題分散，解讀要明說「活動度增加但方向尚未集中」，不得強行寫成單一正面結論。
- 主題代碼不入文；若資料只有代碼，需用 `topic_label`、代表專利文字或欄位名稱轉成自然語言，不能讓使用者在報告中看到內部代碼。

## 單報表重產規則

若任務指定 `report_keys`：

- 先讀入既有 `narratives.json`。
- 只替換指定 `report_keys` 的內容。
- 其他 `report_key` 與其 variants 必須原樣保留。
- 不得輸出只含重產範圍的新檔，避免靜默刪除其他解讀。

## 品質標準

- 每段解讀必須能回扣至少一個 `report_data` 欄位或圖表 artifact。
- 不得把單一圖表擴大成整份策略結論。
- 不得把申請量或申請人家數直接等同競爭力、技術成熟度、產品核心度、市場重要性或商業強度。
- 不得使用「值得關注」「具備潛力」等沒有指向的空話；若使用，必須說明基於哪個資料現象。
- 不得在 narrative 或後續 PPT 文案中顯示「未選」「缺資料」「尚未產出」這類系統狀態；這些只屬於任務進度與 manifest。
- 輸出完成後確認 `based_on_version` 等於報表版本目錄名稱。
