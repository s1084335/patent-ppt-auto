# HTML 情報報表 → 簡報

本檔分兩區：**執行 Runbook**（你要做的事）在前，**開發備註**（設計原因、手動流程、
環境細節）在後。只讀前區就能完成工作。

---

# 執行 Runbook

## 你負責哪兩件事

deck 產製共九步，其中**七步是確定性程式**，由 runner 以子行程跑完，你不會碰到。
需要判斷的只有兩件：

| # | 你要做的 | 輸入 | 輸出 |
|---|---|---|---|
| 1 | **撰稿** | `plan.json`＋`report.json` | `content.json`（唯一輸出檔） |
| 2 | **逐頁目視** | 組版後的逐頁 PNG | 修過的 `content.json`（或回報通過） |

其餘（解素材、排頁、chip 重排、圖表轉 PNG、字數閘門、組版、閘門稽核、轉圖）
runner 會處理，每一步的結構化結果會交給你。

⚠ **你只能寫 `content.json` 一個檔。** 圖表、版面引擎、字級規格都不在授權範圍內
（見「授權範圍」）。

## 第 1 件：撰稿

### 輸入

`plan.json` 已經把每頁要用哪張圖、該章節的判讀原文（`source_texts`）、口徑註記
（`source_notes`）、表格（`source_table`）與各欄位字數上限（`budget_units`）備妥。

- ⚠ **每頁的主圖在 `chart`（單數）**；`charts`（複數）是留給 `content.json` 的空欄位。
  兩個名字幾乎一樣、意義完全不同，拿 `charts` 去找圖會得到空陣列。
- **封面素材不在 `plan.json` 裡**——`plan.json` 只管內容頁。報表層級資訊
  （來源檔名／報表標題／產表參數）在 `report.json` 的 `report_meta`；封面統計數字
  （件數、家族數、受理局數、主題數）在各章節的 `tables`。

讀 `report.json` 時：**`texts` 是報表作者已經寫好的判讀**，是簡報敘事最重要的來源；
`tables` 給精確數字；`notes` 給口徑與資料品質警語（常有「不完整家族 N 個」這類，
要放進限制頁）。

### 濃縮 ≠ 砍字數

每頁只留兩層：

1. 標題下一行**結論句**（≤ 一行）：這頁看完該記得的那句話。
2. 底部**判讀帶**兩行：`一句結論 ＋ 一句支撐`。

寫法與反例見 [references/narrative.md](references/narrative.md)。重點：

- 不用「依據／風險／行動」模組標籤，改讓句子本身帶出角色（「先讀完那 4 件請求項
  再落筆」＝行動）。只在標籤會**改變讀法**的頁面偶爾使用（一份簡報 1–2 頁為限）。
- 判讀要轉成決策語言：布局熱點、成熟度、競爭密度、空白機會、風險牆、可繞開方向；
  不要只說「誰最多、哪年最高」。
- 低件數一律用「低密度、可探索、需驗證」的審慎語氣，不得說成藍海。

### structure_checklist 要逐項清空

三件結構調整已由排頁步驟產出，撰稿就是把 `structure_checklist` 清掉：

1. **訊號少的主題收頁**——同一指標有多個階層（`..._L4`／`..._L5`）時會被列進檢查表，
   看判讀原文確認分類種類夠不夠分頁；不夠就只留最有訊號的一張、其餘轉判讀文字。
   ⚠ 排頁**不會替你判斷訊號足不足**（試過用表格列數當代理值，實測無關），
   只保證你被問到。
2. **「主要玩家在做什麼」骨架頁已自動插入**（在帶 `patent_ids` 的章節之後，
   已帶 `layout: "label"` 與各主體的標籤），只要填內容。
   顆粒度不夠時依「什麼時候該補查請求項」補；**一頁裝不下就拆兩頁**
   （實測 5 家＋演進鏈需要 16 個顯示行，上限 14）。
3. **主題時間線頁要有上層結論**——會被列進檢查表；先給演進階段（技術語言，
   不是「早期／中期」），圖退為證據。

⚠ 骨架頁的 `<待撰稿填寫>` 沒清掉，字數閘門直接擋下——不會交出半成品。

### 頁型與版面容量

**頁數沒有上限**，預設就是「圖表數 ＋ 2」（封面、結論）。要增減頁數用頁型控制：

⚠ 2026-08-18（§7d）：路線圖頁已**併入結論頁**、期程整個拿掉，故 3 改為 2。

| 頁型 | `charts` | 用途 | 代價 |
|---|---|---|---|
| 圖表頁（預設） | 1 張 | 一圖一結論 | — |
| 純文字頁 | 留空 `[]` | 中場小結、方法說明、資料口徑、附錄——**要多幾頁就加這種** | 無圖，`lines` 每則一段，上限約 13 個顯示行（依幾何算出，不寫死） |
| **標籤欄文字頁** | 留空 `[]` ＋ `"layout": "label"` | `主體｜內容` 的定義列表（競爭者構型頁、各家比較） | 左欄吃掉 2.2in；標籤要短（≤ 9.3 單位） |
| 雙圖頁 | 2 張 | **盡量不要用**；只有兩張圖都很扁（如 subclass 總覽）時才成立 | 兩張圖**都必須 ≥12pt**，否則字數閘門直接擋下要求拆頁 |

📏 **文字頁的行長是有上限的，而且預設就超標**。滿版單欄每行約 **50 個全形字**，
遠超中文舒適區間（25–35）；字級鎖死 16pt 不能靠縮字解決，只能切寬度。
`layout: "label"` 把行長降到約 **40 個全形字**，同時讓主體名變成可掃讀的索引。
⚠ **不要改成硬分兩欄**：兩欄各只剩約 23 單位，而「CN 121754861、CN 121754862、
CN 223248694」這類並列號碼單串就超過一行，會被迫斷行，反而更難讀。

3 張以上直接擋掉——那個尺寸的圖沒有閱讀價值。

⚠ **雙圖頁的 12pt 門檻是硬的**（單圖頁是 9pt）。擠成一頁是自找的，所以標準更高。
字數閘門會用與組版相同的幾何**事先預測**兩張圖的字級：兩張高瘦圖（ratio ≈2.1）
併頁只有 4.8pt → 擋；兩張扁平圖（ratio ≈6–8）併頁 12.8pt → 放行但仍提示拆頁。
不要靠感覺判斷哪兩張能併，交給它算。

### content.json schema

範本見 [references/content-template.json](references/content-template.json)。

```python
content = {
  "footer":      "…｜非 FTO／非侵權判斷",     # 每頁頁尾
  # 封面
  "eyebrow": "…", "deck_title": "…", "subtitle": "…",
  "meta": ["資料期間…｜來源…", "報表參數…"],   # 恰好兩行
  "stats": [("<N>", "件專利"), ("<N>", "個家族"), ("<N>", "個受理局"), ("<N>", "個主題")],
  "stats_note": "…", "boundary": "…",
  # 封面不放產出規則；資料口徑集中在附錄或口徑頁。
  # 第 2 頁：綜合結論（唯一的第 2 頁；rec 已於 2026-08-19 §9.3 退場）
  "conclusions": {"title": "…", "takeaway": "…",
                  "covered": "<N/M>", "uncovered": [{"topic": "…", "reason": "…"}],
                  "rows": [{"topic": "…", "finding": "<逐字取自 topic_facts>",
                            "reading": "…", "action": "…", "evidence": "依據：…"}]},
  # 內容頁：一頁一圖
  "pages": [
      {"title": "…", "takeaway": "…（一行）",
       "charts": ["<png 檔名，不含副檔名>"],
       "lines": ["結論句…", "支撐句…"],
       "tag": None},                          # 偶爾用 "風險"／"機會"
      {"title": "…", "takeaway": "…",
       "charts": [], "layout": "label",       # 標籤欄文字頁
       "lines": ["主體｜內容…",               # 「｜」前＝左欄，後＝右欄
                 "沒有「｜」的列會橫跨全寬（警語、小結用）"],
       "tag": None},
  ],
  # 末頁
  # ⚠ 2026-08-18（§7d）：`roadmap*` 三個鍵已移除——路線圖頁併入結論頁、
  #   期程整個拿掉。期程（「短期 0–3 個月」）是全份唯一沒有資料支撐的欄位：
  #   系統不知道人力、預算與產品排程，那個數字必然是編的。
  "limits_title": "分析限制與適用邊界",         # 可省略
  "limits": ["…", "…", "…"],                  # 每則一行
}
```

P2 evidence gate：結論頁**每一列**必須在 `evidence` 或 `reading` 中帶 `依據：`
（2026-08-19 §9.3：`recommendations` 已退場，這條紀律移到結論頁——它擋的是「接不上依據的建議句」，而結論頁的行動同樣是建議）；`本簡報怎麼讀`、`圖表原則`、`待驗證`、`降級` 是內部流程或規則字串，
不得印在投影片上。

`依據：` 後面必須是可追錨點，不能寫空泛依據。合格錨點至少要讓讀者知道它追到哪：
專利號、claim 編號、topic code、申請人／權利人、family、country、年份區間、具體件數、
圖表或表格的中文顯示名稱。禁止例句：`依據：整體統計`、`依據：資料分析`、`依據：報表結果`、
`依據：趨勢觀察`、`依據：專利資料`、`依據：AI 判斷`。內部欄位 key 不得直接上投影片：
例如 `family_country_layout` 要寫成 `家族國家布局`。如果找不到可追錨點，不要產生該建議；
改併入 `limits` 或省略。

⚠ **結論列數沒有上限也沒有下限**（2026-08-19 §9.3）：原本 rec 有「3–5 個方向」的數量鎖，使用者裁決「不一定只能提四項，需要的是完整由資料驅動所得出的結論」。完整性改由行動空間完整掃描保證（§9.6），不用數量門檻。

### 色彩庫（挑名字，不寫色值）

色彩庫與版型庫一樣是**給你挑的清單**——挑名字、不寫 hex，同
`layout: "chart"` 而不是寫幾何。挑庫外的色會被 `check_content` 擋下。

| `color` | 什麼情況用 |
|---|---|
| `cyan` | 中性強調：陳述事實、不帶評價的重點 |
| `blue` | 需要進一步驗證的方向（still open） |
| `amber` | 需留意但未到風險：擁擠、集中、可探索 |
| `rose` | 風險或應迴避：高競爭、權利集中在他人 |
| `green` | 可行動、已有依據支撐的結論 |

⚠ 唯一定義處是 `deck_layout.COLOR_LIBRARY`；本表由它同步，測試
`test_color_library.py` 盯著兩邊一致。要新增顏色先改那裡並補「什麼情況用」
——沒有用途說明的顏色，下一個人只能靠名字猜。


### 自我指涉的地方一律用佔位符

簡報講自己的地方最容易錯，而且**沒有任何閘門抓得到**——它不是版面問題也不是
數字問題。封面頁碼一律用 `{chart_first}` / `{chart_last}` / `{last}` / `{n_charts}`，
字數閘門會擋掉寫死的頁碼。其他像「本報告共 N 頁」「詳見第 N 頁」也一樣，
能導出就不要手寫。

## 什麼時候該補查請求項（預設：不查）

報表判讀原文是**二手轉述**：作者已經把請求項消化成「〈某元件〉連動〈某元件〉」
這類概括說法。對多數頁面這個顆粒度夠用；**只有一種頁面會不夠**——「主要玩家在
做什麼」。RD 要拿去比對的是請求項用語，二手轉述會漏掉真正的區別：報表寫成同一個
構型名的兩件專利，獨立項讀下去可能是兩套完全不同的機構（實際遇過，而且正是該頁
最有價值的發現）。

**三個條件同時成立才查**：

1. 該頁的用途是**逐案機構比對**（競爭者構型頁），不是統計或趨勢；
2. 報表判讀在該處只給了概括說法，看不出各家的差異在哪；
3. 報表的 Key Players 表有 `patent_ids` 明細——**有 ID 才查得動，也才回溯得了**。

**怎麼查**：用配給你的**唯讀 MCP 取證工具**。`plan.json` 的 `claim_lookup.players`
已經把 Key Players 表的 `patent_ids` 解析好，**不要自己去表格挖 ID**——實際踩過：
用終端輸出讀 HTML 片段時中文編碼破損，差點把某家的 ID 當成另一家的。

**四條硬規則，一條都不能省**：

| 規則 | 為什麼 |
|---|---|
| **只讀不寫** | 取證通道是唯讀的；不落任何檔、不改任何資料 |
| **只補敘述，不補統計** | 件數／家族數／授權數一律以報表為準。資料庫現況與報表快照可能不同調，混用會讓同一份簡報出現兩個口徑 |
| **每個新名詞標來源專利號** | 沒有專利號的機構名詞＝無法回溯＝等同推測 |
| **斷言範圍＝證據範圍** | **取回 ≠ 讀過**。讀了 7 件就只能講那 7 件；要寫「三代都…」「各家一律…」這種通則，就得把範圍內的**每一件都讀完**。中間這一步沒有任何閘門會提醒你 |
| **在該頁揭露來源** | 加一行「本頁機構名詞取自各案獨立項原文（專利資料庫唯讀查詢）」。封面來源標示要不要一起改，問使用者 |

**不該查的情境**（問了也不會更好，只會製造口徑衝突）：補件數、驗證報表數字、
補報表沒有的統計、把資料庫的最新法律狀態蓋掉報表快照。

⚠ 設計案通常沒有請求項（字數 0），那是正常的，不是查詢失敗。

## 第 2 件：逐頁目視迴圈

組版完成後 runner 會給你**逐頁 PNG**。這一步是簡報品質的最後一道，
**不是形式檢查**——程式化閘門過了不等於版面沒問題，量測是估算，
實際換行由 PowerPoint 決定。

逐頁確認：

- 文字沒溢出卡片、沒重疊
- 圖表沒被裁切
- 圖內字看得清楚
- 版面平衡
- **放大到 2× 以上看行首有沒有中文標點**（全頁縮圖看不出來，眼睛會自動把標點
  讀回上一行；見 [pitfalls.md](references/pitfalls.md) #41）

⚠ **不得抽樣。** 抽看幾頁就回報，等於把沒看的頁默認為沒問題。

### 發現問題只能改 content.json

合法動作只有四種：**縮寫、改寫、拆頁、轉純文字頁**。
圖表、版面引擎、字級規格照授權界線不得動。改完 runner 會重組版、重轉圖，再給你看。

**迴圈上限是產線參數**（`DECK_VISUAL_LOOP_MAX_ROUNDS`，預設 4）。達上限即
任務失敗並附最後一輪的目視發現——不要為了收斂而砍內容，砍字正是
[narrative.md](references/narrative.md) 明文禁止的。字數閘門的紅走同一個迴圈、
吃同一個參數，不另設第二條重試路。

⚠ **每一輪都要留紀錄**（發現了什麼、改了 `content.json` 哪裡）。
那是日後校準這個參數的唯一依據。

## 閘門怎麼讀

| 閘門 | 通過條件 | 不過怎麼辦 |
|---|---|---|
| 字數／裸數字（組版前） | 無 `<待撰稿填寫>`、欄位不超上限、雙圖頁預測 ≥12pt | 依提示縮寫或拆頁 |
| 版面裕度（組版時） | **溢出區域：0 個** | 縮短該處文字 |
| 字級稽核（組版後） | 字級只有 24／16；圖片內容雜湊去重為 0；頁數正確 | 回頭改 `content.json` |
| 圖內字級（組版時逐張列出） | 單圖頁 ≥9pt、雙圖頁 ≥12pt | 見下方優先順序第 3 條 |

⚠ **「判讀帶建議 ≤100 單位」實務上幾乎每頁都會超**（110–140 常見），因為報表判讀
原文每段都很長。**它是警告不是閘門**，真正的判準是組版後圖內字級仍 ≥9pt。
不要因為看到一排警告就去砍內容。

⚠ **裸數字是警告不是閘門**，逐條看過再決定。簡報上的數量**一律要帶量詞**，
裸數字會被讀者當成瑕疵指出來。合法例外只有三種：量詞涵蓋整串
（「2020、2022、2024 年」）、年份、報表編號；封面數字磚的量詞在下方 label，
掃描器已豁免。⚠ 補量詞會讓字數變長，可能撞到欄位上限（實際發生過：封面
`stats_note` 補完超標 2.9 單位）。改寫時**不要為了塞得下又把量詞拿掉**——
換句子結構，別換回裸數字。

## 數字回溯（必做）

簡報上每個數字都要能在報表的表格或判讀文字裡指出來源。
⚠ **不得自行相加**。實際踩過的坑：把「甲公司 11 件已授權」與「乙公司 10 件已授權」
相加寫成 21，但兩者有 12 件是共同申請——重複計算。跨列相加前先問
「這兩列會不會涵蓋同一批專利」。

## 優先順序（衝突時照這個判，不要自己權衡）

目標互相打架時，**編號小的贏**。這條梯子是本 skill 所有取捨的唯一依據。

1. **數據正確** — 數字可回溯到報表的表格或判讀文字；不跨列相加；不推算、不補值。
   任何版面或美觀理由都不能動它。做不到就不做那一頁。
2. **不誤導** — 低件數只能說「低密度、可探索」；件數／家族數／法律狀態分開講；
   刻意略過的圖、沒驗到的項目要揭露。**寧可頁面難看，不可讓讀者做錯判斷。**
3. **可讀** — 單圖頁圖內字 ≥ 9pt、**雙圖頁 ≥ 12pt**、文字不溢出、不重疊、圖不裁切。
   與下面任何一項衝突時，一律**加頁**解決；雙圖頁預設不用。
4. **結論可用** — 每頁一句結論句；第 2 頁是研發建議結論；判讀是決策語言不是描述。
5. **判讀完整度** — 判讀帶想講多少。
6. **頁數精簡** — **最低**。頁數永遠不是限制，不得為了少一頁而犧牲上面任何一項。

### 常見衝突的判法

| 衝突 | 判法 |
|---|---|
| 判讀寫不下 2 行 | 先依 [narrative.md](references/narrative.md) 濃縮（**濃縮≠砍字**）；仍不夠可放到 4 行；再不夠就把溢出的內容移到**新增的純文字頁**，不准縮圖 |
| 判讀撐到圖內字 < 9pt | 3 > 5：縮判讀、加頁，不是縮圖 |
| 圖太多、頁數很長 | 3、6：不合併，維持一頁一圖。真要併只能併扁平圖，且兩張都要 ≥12pt |
| 圖內字 < 9pt 且判讀已精簡 | chip 型 → 重排；其他 → 照原樣交付，但**必須在回報中列出該頁字級**（2 > 3） |
| 使用者要求與本 skill 預設不同 | 使用者優先——**但第 1、2 條是底線，不因指示而放寬**；衝突時說明後再做 |

組版會把低於 9pt 的頁面連同「該怎麼處理」一起印出來，照做即可。

## 授權範圍

- ✅ **chip 型機會四象限可重排**。使用者已於 2026-08-11 給予常設授權：
  「只有技術／功效機會四象限可以重排」。排頁步驟會自動標出這類圖，runner 直接跑，
  **不用再問**。重排只動版面（chip 改一行一個、壓低高度），文字、顏色、tooltip、
  象限歸屬全部照抄。
- ❌ **其他圖表一律不得重排或重畫**，即使字級偏小。要改先問使用者。
- ❌ 任何會改變圖表**數值或視覺結論**的動作，一律禁止，授權也不做。
- ❌ 版面引擎、字級規格、配色不在授權內。

## 完成回報格式

1. 用了哪些報表章節、哪些圖表（含刻意不用的與原因）
2. 第 2 頁研發建議摘要
3. 是否補查請求項：**沒查**就說明玩家頁的顆粒度止於報表判讀原文、且該頁已標明
   這個邊界；**查了**就列出補查的主體與件數、每個新名詞的來源專利號，以及該頁的
   來源揭露
4. 品質檢查結果：字級稽核、圖表去重、裕度檢查、逐頁目視範圍、數字回溯
5. 目視迴圈：跑了幾輪、每輪發現什麼、改了哪裡
6. **據實揭露沒做到的部分**：例如某張圖的字級受限於原圖結構、頁數超出原訂範圍及原因

## 流程細節

### 1. Source intake — 解出素材

產出 `work_dir/charts/*.svg` 與 `work_dir/report.json`（章節、表格、判讀文字、
圖表清單）。

⚠ **圖表不是外部檔案**，是 URL-encoded 的 data URI 內嵌在
`<img src="data:image/svg+xml,...">`。用有長度上限的 regex 去撈 `src` 會一張都撈不到，
然後誤判成「報表沒有附圖」。`scripts/extract_report.py` 已處理。
同一張圖常有 `.web.svg` 與非 web 兩版，腳本以內容雜湊去重。

### 2. Evidence mapping — 圖表分配（`scripts/plan_deck.py` 自動）

規則已寫進腳本，不需人工判斷：

- **一頁一張圖**，每張圖只用一次；依報表章節順序排頁。
- **排名類只保留前 10**：檔名或章節帶「_more／第 11–20 名」的圖自動剔除，
  並列在 `skipped_charts`（回報時要說明）。
- ⚠ **頁數要配訊號量，不是配圖表數**。同一主題有多張圖（IPC 4/5 階、CPC 4/5 階）時：
  分類種類多、有跨域訊號 → 分頁講；**分類種類少（例如 subclass 只有兩種、
  CPC 只有個位數）→ 收成一頁「分類碼告訴我們什麼」**，主圖放最有訊號的那張，
  其餘轉成判讀文字。訊號不足的圖可以不放，但**必須在完成回報中列出未使用的圖與原因**。
  ⚠ 這條優先於「所有圖都要用」——四頁講「分類就只有一種」是浪費讀者的注意力。
- chip 型圖表（SVG 內含 `class="chip"`）標記 `rebuildable_chip_chart`。

### 3. 版面與字級

固定規格：16:9、**標題 24pt、內文 16pt**、每頁一句結論、圖表旁必附判讀。

🎨 **配色已定案（2026-08-11），不隨批次更動**：頁面淺藍灰 `#E9EEF6`（淺色系、非純白）、
文字面板 `#DAE4F2`、圖表卡白色（襯出報表原圖）、文字深海軍藍 `#0B2545`、
重點色深藍 `#026AA7` / 赭 `#A15307` / 深紅 `#B0123C` / 深綠 `#046B4E` / 靛 `#433BC4`。
色值寫在 `scripts/deck_layout.py` 檔頭；**不要為個別批次改色**，要改請先問使用者
並同步改這裡。

⚠ **字級被鎖死就不能靠 autofit**。`scripts/deck_layout.py` 的做法是先量再配：
每個文字區用 `text_h()` 估高（CJK 1.0 em、半形 0.55 em、×1.06 安全邊界），
判讀帶依需求撐高，**剩下的高度才給圖表**，圖表永遠等比縮放置中、絕不裁切。

⚠ **不要全域統一放大圖內字級**。報表圖表的標籤欄寬、chip 背景寬都是用原字級算死的，
放大會讓長條圖類別標籤蓋到長條、chip 文字衝出色塊——而且只發生在少數幾張圖，
抽看抓不到。`scripts/fit_render_charts.py` 會先記錄原字級下「本來就有」的重疊，
再由大到小試，出現**新**重疊就退一級。容忍值分兩種：`text↔text` 3px
（getBBox 含行距留白，貼邊不算撞字）、`text↔rect` 1px（文字碰到長條或色塊是
看得出來的瑕疵）。
⚠ 動過容忍值就**必須重看受影響的圖**——收緊容忍值會把「本來就微疊」的元素納入
基準線，反而放寬它的成長空間，字級可能不降反升。

📐 **關鍵幾何**：投影片上的圖內字級 ≈ 圖內字級 × (可用高度 × 72) ÷ SVG 高度——
**只跟 SVG 高度有關，跟寬度無關**。所以 1180px 寬、字級 15.1 的圖，
在 16:9 版面上最多只能到 9–13pt；使用者若要求「圖上的字 14pt」，那是幾何上做不到的，
**要直接說明並給選項**，不要默默做一個達不到的版本。

### 4. 驗證分層

**第一層：程式化，涵蓋全部**——裕度表（`溢出區域：0 個`）、字級稽核、圖片內容雜湊
去重、頁數；組版同時印出每張圖在投影片上的**實際字級**。

**第二層：實物，逐頁目視**——⚠ 程式化檢查過了不等於版面沒問題，量測是估算，
實際換行由 PowerPoint 決定。若改動只換了色票、版面幾何完全沒動，可註明
「其餘 N 頁幾何與上一版相同（上一版已逐頁看過），本次只換色票並已跑裕度檢查」
——但要在回報中據實寫出來，不能含糊帶過。

**第三層：自我指涉檢查**、**第四層：數字回溯**、**第五層：量詞**——見前區。

## 為什麼不自己接 psycopg

`scripts/fetch_claims.py` 走專案既有的 `query_database`，帶單句 SELECT／WITH 白名單
與 `SET TRANSACTION READ ONLY`（唯讀綁在**交易**上，因為 Supabase pooler 會忽略
連線字串的 startup options）。自己接等於繞過這層。

產品側不跑這支——取證改走唯讀 MCP 工具，介面本身就是護欄（typed 參數、
工具清單即能力清單）。`fetch_claims.py` 保留給開發側手動流程。
