# 匯出報告 PPT 文案規則

本檔是「匯出報告」PPT 文案產製服務的 runtime 規則來源。`ai:report_ppt` payload 必須載入
本檔內容；`SKILL.md` 只保留流程與產品契約，不重複維護全文規則。

## 分工邊界

PPT 階段的 AI **只產一個 slot**：`direction.body`。其餘頁面的標題與要點一律來自
逐報表解讀（`narratives.json`），封面主標由 workspace 名稱確定性組成
（2026-07-31 起 `cover.title` 退場），附錄頁沒有文案槽。這個收斂是刻意的：同一段判讀
若在解讀與 PPT 文案各寫一次，兩邊遲早互相矛盾，而讀者無從判斷哪個才算數。

- 只產敘述文字，不決定排版、不決定版型、不調整座標；PPTX 由組版程式依 `theme.json` 組出。
- 不新增、不重算、不四捨五入、不改寫引擎數字；所有數字只以 `report_data` 為準。
- `narratives` 只作語意脈絡；若 `narratives` 與 `report_data` 衝突，以 `report_data` 為準。
- 只談 `report_data` 裡實際存在的報表。未選、無資料或被標為缺漏的報表不得入文，也不得憑常識補充。
- 不得在 PPT 中提示缺漏。PPT 是使用者選擇後的正式產物，不出現「未選」「缺資料」
  「尚未產出」這類系統狀態；缺漏只進任務進度與 manifest。
- 主題代碼（`T001`、`M01` 這類）不入文，要寫成使用者讀得懂的技術描述。
- 解讀不確定處保留「需人工覆核」措辭，不把推測寫成結論。

## 報告敘事主線

整份 PPT 不是逐頁孤立摘要，而是要把「申請趨勢 → 技術分布 → 競爭者佈局 → 機會評估 →
主要玩家」串成一條研發或專利主管讀得懂的判讀線。

- 先判斷本次資料的整體態勢：量能集中或分散、時間上升或平穩、地域與玩家是否集中。
- 再把技術分布連到競爭者佈局：哪些技術主題由哪些申請人或權人支撐，哪些只是弱訊號。
- 再把機會評估連到行動建議：只提「後續可優先檢視」「可作為研發題目候選」
  「需先覆核代表專利」這類低承諾結論，不直接下投資或產品化指令。
- 若各頁訊號互相不支持（例如趨勢上升但技術分布分散），必須明說「量能增加但方向尚未集中」
  這類整合判讀，不得硬寫成單一好消息。
- 各頁文案要有頁間脈絡，但不得編造因果關係，也不得為了串接故事而補不存在的關聯。
- `direction.body` 是整份報告的收斂點，必須吸收本次實際包含的全部報表重點；各頁解讀回扣該收斂的一部分。

## 逐 slot 寫法

文案要能直接放進 PPT，不要輸出「以下是」「本段說明」「根據資料可知」這類產製說明。

`direction.body`＝**結論頁**（倒數第二頁、附錄之前），整合本次有資料的全部報表。
輸出**必須是單一 JSON 物件字串**（組版依它畫「態勢→機會→方向」色塊流程＋
研發題目卡片＋核心結論條；2026-07-31 合併版定案）：

```json
{"situation": ["2022 起放量，2022 年 15 件為高峰", "布局與有效保護皆集中中國"],
 "opportunity": ["滑雪擬真省空間 7 件 6 家，是核心區唯一無龍頭卡位的縫隙"],
 "direction": ["以阻力調節差異化切入，前提是迴避設計"],
 "topics": [
   {"name": "可調阻力結構", "basis": "必守核心區既有權利擁擠", "action": "先做迴避設計檢索"},
   {"name": "省空間結構", "basis": "7 件 6 家、無龍頭卡位", "action": "可作專利卡位候選"}
 ],
 "conclusion": "同業加速進場、技術處於成長期，現在是投入研發與專利卡位的關鍵窗口"}
```

| 欄位 | 寫法 | 硬限制 |
|---|---|---|
| `situation`／`opportunity`／`direction` | 各 1–3 句短判讀（色塊內逐行呈現） | 每句 ≤28 字；不空 |
| `topics` | 2–3 個具體研發題目卡 | `name` ≤12 字；`basis`／`action` 各 ≤20 字；依據必須對得到報表數據 |
| `conclusion` | 整份報告一句話收束（底部深藍條） | ≤40 字；低承諾語氣（檢視／候選／覆核），不下投資指令 |

不得輸出 JSON 以外的文字；不得把單一圖表結論擴大成整份策略；
不得寫「建議投入」卻沒有資料支撐。

## 內容品質標準

- **判讀式而非裸名詞**：每個判斷都要說「所以呢」。「A63B 47 件」是數字，
  「技術布局高度集中於 A63B 健身器材本體」才是判讀。
- **證據對齊**：每一句都要能對應到一個 `report_data` key 或一段 `narratives`；
  沒有來源的判斷必須刪除或改成待確認。
- **數字保真**：引用數字時使用 `report_data` 內已有的值，不新增、不重算、不四捨五入。
- **跨頁一致**：`direction.body` 不得和各頁解讀互相矛盾；各頁可互相呼應形成頁間脈絡，但不得編造因果鏈。
- **語氣**：繁體中文，面向企業內部決策與研發討論；句子短、資訊密度高，
  避免「值得關注」「具備潛力」這類沒有指向的空話。
- **不確定性**：只有已出頁、已入文的報表樣本偏少、分群粗略或訊號弱時才用限制語氣；
  未選或無資料的整張報表不說明、不補寫、不提示。
- **舊版內容禁用**：不得出現已移除的市場規模、痛點交叉驗證、`market.*`、`pain_point.*`
  或外部市場研究結論。

## 各報表判讀口徑

`direction.body` 引用各報表時遵守下列口徑，避免超譯：

- `application_trend`／`publication_trend`：講時間區間、活動度變化、峰值或平穩；
  最近 1–2 年件數偏低多為審查中的資料截止效應，不得寫成衰退，也不得預測未來成長。
- `country_distribution`：講保護地域與布局集中度；不得推論銷售市場或需求大小。
- `ipc_main_distribution`／`cpc_main_distribution`：講分類集中度與階層之間的落差；
  4 階與 5 階是不同母體，不得把兩者的數字混著講。
- `cluster_topic_table`：講主題集中、分散、長尾與代表性技術群；分群標籤僅供辨識，
  技術優劣與可商品化程度未經驗證。
- `applicant_ranking`／`owner_ranking`：講主要玩家與集中度。申請人家數衡量的
  是競爭者是否已進場，不等於市占、營收、產品核心度或合作關係；
  不得把「很多人做」超譯成「這個很重要」，也不得把申請量直接等同競爭力。
- `applicant_country_distribution`：講玩家與地域的交叉訊號；不得推論公司策略已定案。
- `opportunity_quadrant`：講象限名稱、象限判讀與後續檢視點，並回扣件數與申請人家數
  相對門檻的位置；不得寫成投資指令，不得保證空白區一定可進入。

## 本 skill 消費的解讀契約（上游 `ai:narrative` 產出）

各頁標題與要點直接取自 `narratives.json`，格式如下：

```json
{"headline": "技術布局高度集中於 A63B 健身器材本體",
 "points": [
   {"label": "現況", "text": "A63B 47 件，F03G 僅 2 件", "emphasis": true},
   {"label": "意涵", "text": "同一技術方向反覆布局，非跨領域分散"},
   {"label": "後續", "text": "以 5 階細分類檢視內部斷層"}],
 "text": "（長文，供報表頁使用，PPT 不用）"}
```

- 頁標題＝`{報表主題}：{headline}`，所以 `headline` 要寫成判讀句而非名詞片語，
  控制在 26 個中文字以內才不會佔滿兩行。
- `points` 建議 3 條，每條 `text` 以 30–50 個中文字為度；`emphasis: true` 的條目會用
  警示紅呈現，只給真正需要提醒的一條。
- 缺 `headline`／`points` 時組版會退回長文 `text`：依段落標記切條、依版面截斷，並寫入
  manifest 警告。能跑，但標題與要點都會被截，簡報品質明顯下降——這是上游要補齊的契約，
  不是組版可以彌補的。
