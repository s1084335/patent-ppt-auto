# 匯出報告 PPT 文案規則

本檔是「匯出報告」PPT 文案產製服務的 runtime 規則來源。`ai:report_ppt` payload 必須載入本檔內容；`SKILL.md` 只保留流程與產品契約，不重複維護全文規則。

## 分工邊界

- 文案產製服務只產生各 slot 的敘述／解讀文字。
- 不決定排版、不決定版型、不調整座標；PPTX 由 `build_ppt.py` 依 `theme.json` 組版。
- 不新增、不重算、不四捨五入、不改寫引擎數字；所有數字只以 `report_data` 為準。
- `narratives` 只作語意脈絡；若 `narratives` 與 `report_data` 衝突，以 `report_data` 為準。
- 缺資料報表不得入文：只討論本次實際產出的報表；未選、無資料或 manifest 標為缺漏的報表不得出現在 PPT 文案中。
- 不得在 PPT 中提示缺漏：缺漏只進任務進度、manifest 或後台追蹤；PPT 是使用者選擇後的正式產物，不顯示「未選」「缺資料」「尚未產出」這類系統狀態。
- `direction.body` 必須綜合本次實際包含的全部報表與 narratives，不得只看單一分群或單一圖表。
- 各頁文案要有頁間脈絡，但不得編造因果關係，也不得為了串接故事而補不存在的關聯。

## 報告敘事主線

整份 PPT 不是逐頁孤立摘要，而是要把「申請趨勢 → 技術分布 → 競爭者佈局 → 機會評估 → 主要玩家」融會貫通成一條可被研發或專利主管讀懂的判讀線。

- 每張報表的解讀不能過度擴大，也不能只講數據。頁面文案要從該頁數據現象出發，說明專利布局或研發初篩意義，再收斂成可人工確認的關注點。
- 單頁不得獨自推出市場重要性、產品核心度、技術成熟度或公司策略；但也不得只列「前幾名、幾件、哪一年」而沒有解讀意義。
- 先判斷本次資料呈現的整體態勢：量能集中或分散、時間上升或平穩、地域與玩家是否集中。
- 再把技術分布連到競爭者佈局：哪些技術主題由哪些申請人或權人支撐，哪些只是分群上的弱訊號。
- 再把機會評估連到行動建議：只提出「後續可優先人工確認」或「可作為研發題目候選」等低承諾結論，不直接下投資或產品化指令。
- 若各頁訊號互相不支持，例如趨勢上升但技術分布分散，必須明說「量能增加但方向尚未集中」這類整合判讀，不得強行寫成單一好消息。
- `direction.body` 必須吸收各頁重點，形成整份報告的總結；各頁 narrative 則回扣該總結的一部分，避免每頁像獨立報表摘要。

## 有無市場資料時的報表重點

第一版 PPT 已移除市場規模頁與痛點交叉驗證頁；但若系統已有經確認的市場資料，報告解讀可以把它納入「研發方向優先序」的背景。重點不是套同一段限制語，而是依資料可用性改變相關報表的判讀重心。

| 情境 | 相關報表重點 | `direction.body` 寫法 | 禁止 |
|---|---|---|---|
| 有市場資料 | 先讀市場資料對應的應用、區域、需求或限制，再回扣 `application_trend`、`country_distribution`、`cluster_topic_table`、`applicant_ranking`、`opportunity_quadrant`，判斷哪些技術群與玩家佈局和市場背景較一致 | 說明「專利布局訊號」與「市場資料訊號」是否互相支撐；若支撐，提出可優先人工確認的研發題目；若不支撐，指出需要補查的落差 | 不得新增市場規模數字；不得把市場資料直接當成專利機會已成立；不得把外部市場結論覆蓋專利資料 |
| 無市場資料 | 只用專利報表本身：申請／公開趨勢看技術活動度，地域分布看保護範圍，技術分布看主題集中度，競爭者佈局看主要玩家，機會象限看相對空白或擁擠區 | 明確定位為「專利布局與研發方向初篩」；可提出候選方向與需人工確認點，但不得下市場需求或商業優先序結論 | 不得用常識補市場需求、痛點、TAM/SAM/SOM、價格、銷售或客戶判斷；不得在 PPT 中寫「沒有市場資料」或「缺市場資料」 |

有市場資料時，市場資料只回答「應用需求或商業背景是否支持某些方向」；專利報表仍回答「技術與競爭布局是否已有訊號」。無市場資料時，報告仍可成立，但結論必須收斂在專利情報與研發初篩，不延伸到市場可行性。

## 各報表解讀重點與口徑守則

- `application_trend`／`publication_trend`：重點是時間區間、活動度變化、峰值或平穩狀態；不得直接預測未來成長。
- `country_distribution`：重點是保護地域與布局集中度；不得推論市場銷售區或需求大小。
- `cluster_topic_table`：重點是主題集中、分散、長尾與代表性技術群；主題代碼不入文，例如不要寫「M01」「T03」，要寫成使用者可讀的技術描述。
- `applicant_ranking`／`owner_ranking`：重點是主要申請人／權人與集中度。申請人家數衡量的是競爭者是否已進場，不等於產品核心度；不得把「很多人做」超譯成「這個很重要」、市場重要性、營收、市占或合作關係。
- `applicant_country_distribution`：重點是玩家與地域佈局的交叉訊號；不得推論公司策略已定案。
- `opportunity_quadrant`：重點是相對空白、擁擠、可優先人工確認的區域；不得寫成投資指令或保證機會。
- 若某報表缺資料，該報表重點不得被其他報表或常識補寫，也不得在總結中點出缺漏；直接不談該報表。

## 逐 slot 文案規則

所有 slot 文案都必須可直接放進 PPT，不要輸出「以下是」、「本段說明」、「根據資料可知」這類產製說明。除 `cover.title` 外，優先採用「觀察 → 意涵 → 決策提醒」的寫法；每一句都要能回扣 `report_data` 或 `narratives`。若某報表未選或無資料，直接不談；若已出頁的報表內部樣本偏少或訊號弱，只能在該頁用限制語氣說明，不得寫成系統缺漏。

| slot | 目標 | 寫法 | 禁止 |
|---|---|---|---|
| `cover.title` | 讓使用者一眼知道本份 PPT 的分析範圍 | 12–24 個中文字為主；可放技術範圍、產品範圍或報表版本語意；語氣正式、可對外簡報 | 不放市場規模、痛點、投資、保證性成果；不放沒有來源的產業口號 |
| `direction.body` | 作為第 2 頁總結，整合本次有資料的全部報表 | 3–5 個短句或換行段落；先講整體態勢，再講主要研發方向，最後指出需要人工確認的取捨；必須涵蓋趨勢、技術分布、競爭者或機會評估中實際存在的資料，並說明有無市場資料對結論邊界的影響 | 不得只看分群；不得把單一圖表結論擴大成整份策略；不得寫「建議投入」但沒有資料支撐 |
| `trend.narrative` | 解讀申請／公開趨勢 | 指出年份區間、峰值或明顯變化；若趨勢平緩，說明穩定或資料不足；可連到後續技術或競爭者頁，但不得製造因果 | 不得預測未來必然成長；不得把資料缺口寫成下降；不得新增圖上沒有的年份與數字 |
| `tech.narrative` | 解讀技術分布與分群結果 | 說明主題集中度、主要技術群、長尾或分散現象；若 topic 名稱較粗，保留不確定性並提醒需人工看代表專利 | 不得宣稱技術優劣、成熟度或可商品化程度；不得把 cluster topic 當成已驗證技術路線 |
| `competitor.narrative` | 解讀申請人／專利權人與地域佈局 | 點出主要玩家、集中或分散程度、跨地域佈局；必要時區分申請人排名與專利權人排名；申請人家數只代表競爭者是否已進場 | 不得推論市占率、營收、合作關係或商業強弱；不得把申請量直接等同競爭力、產品核心度或市場重要性 |
| `opportunity.narrative` | 解讀機會四象限 | 說明象限中的相對位置、可優先觀察的低競爭或高潛力區域，以及需要進一步驗證的限制 | 不得寫成投資指令；不得保證「空白機會」一定可進入；不得用未產出的痛點／市場資料補強 |
| `key_players.summary` | 摘要主要專利權人與申請人 | 以名單、集中度與角色差異為主；若 owner 與 applicant 結論不同，分開說明 | 不得把名單直接解讀成合作、併購或授權對象；不得加入資料中不存在的公司 |
| 附錄表格頁 | 不需要 AI 文案 | 保留 deterministic 表格與資料排序；若需要說明，由頁面標題與表頭承擔 | 不為附錄硬生 narrative；不重寫表格數字 |

## 內容品質標準

- 證據對齊：每個非空 slot 至少要能對應到一個 `report_data` key 或一段 `narratives`；沒有來源的判斷必須刪除或改成待確認。
- 數字保真：不得新增、四捨五入、重算或改寫引擎數字；若要引用數字，必須使用 `report_data` 內已有值。
- 報表邊界：只討論本次實際產出的報表；未選、無資料或 manifest 標為缺漏的報表不得出現在 PPT 文案中，也不得在 PPT 內提醒缺漏。
- 跨頁一致：`direction.body` 是總結，不得和各頁 narrative 互相矛盾；各頁可互相呼應，但不得編造因果鏈。
- 融會貫通：至少在 `direction.body` 形成跨報表整合判讀；各頁 narrative 不得只重述圖表標題，必須指出該頁和整體研發方向、競爭佈局或機會評估的關係。
- 語氣要求：使用繁體中文，面向企業內部決策與研發討論；句子短、資訊密度高，避免「值得關注」「具備潛力」這類沒有指向的空話。
- 不確定性處理：只有已出頁、已入文的報表內部樣本小、topic 粗略或訊號弱時，才用限制語氣；未選或無資料的整張報表不說明、不補寫、不提示。
- 舊版內容禁用：不得出現已移除的市場規模、痛點交叉驗證、`market.*`、`pain_point.*` 或 WebSearch 市場研究結論。
- 簡報可讀性：每個 narrative slot 以 80–160 個中文字為上限；若需要條列，用換行分隔，不要輸出 Markdown 表格或過長段落。
- 完成前自檢：確認 slot key 全部合法、沒有新增數字、沒有提及缺漏報表、沒有舊市場線內容、沒有把申請量或申請人家數直接等同競爭力、產品核心度或市場重要性。
