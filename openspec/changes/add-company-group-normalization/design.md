# Design: Company Group Normalization

## Context

The current governance layer uses `derived_layer.company_aliases` to resolve WIPS company code / alias values into a company-level display name. Reporting then groups by `applicant_display_name`.

Group normalization is a second layer above that result. It answers a different question:

- company normalization: "which names/codes are the same company display entity?"
- group normalization: "which normalized companies should be analyzed together as one corporate group?"

## Data Model

Preferred shape:

- `derived_layer.company_groups`
  - `group_id`
  - `group_name`
  - `normalized_group_name`
  - `review_status`
  - `source_type`
  - timestamps
- `derived_layer.company_group_members`
  - `group_id`
  - `company_code`
  - `company_display_name`
  - `review_status`
  - `source_type`
  - `evidence_json`
  - timestamps

`review_status` should distinguish at least:

- `suggested`: generated by CLI/AI, not active for reports.
- `confirmed`: user accepted and active for reports.
- `rejected`: user rejected suggestion.

If implementation finds an existing table can safely represent this without mixing company alias semantics, it may use that table only if the OpenSpec contract remains the same.

## Source Boundary

Only two source paths are in scope.

### Manual User Source

Internal users use browser UI to:

- create a group,
- rename a group,
- add/remove normalized companies,
- confirm suggested members,
- reject suggested members.

These actions write confirmed/rejected state through backend APIs.

### CLI/AI Suggestion Source

CLI/AI may:

- read normalized company names, WIPS codes, aliases, current group mappings, and report context,
- generate candidate group suggestions,
- provide evidence, confidence, and warning flags,
- persist suggestions only through a backend-controlled suggestion/writeback endpoint or workflow output.

CLI/AI suggestion is semi-automatic:

- default evidence source is internal project data only,
- future web access, if explicitly enabled, remains evidence-only and must not confirm mappings,
- a confident candidate requires at least one of: confirmed group seed, user-provided target group/report goal, or high-confidence internal alias/name pattern,
- when that basis is missing, CLI/AI must return `insufficient_evidence` instead of inventing a group.

CLI/AI must not:

- create `confirmed` group rows,
- change confirmed memberships,
- delete groups,
- change source patent/company data,
- silently change report default scope.

## Derived Projection

Derived/report data should expose group fields such as:

- `applicant_group_display_name`
- `current_assignee_group_display_name`
- `recent_assignee_group_display_name`

Fallback:

```text
confirmed group name exists -> group display name
otherwise -> company display name
```

Suggested/rejected mappings must not affect derived report fields.

## Reporting

Existing company-scope reports remain company-scope:

```text
GROUP BY applicant_display_name
```

Group-scope reporting must be explicit:

```text
GROUP BY applicant_group_display_name
```

Acceptable implementation options:

- add parallel group report definitions, or
- add a report scope parameter that explicitly switches grouping fields.

The UI and CLI output must label the chosen scope as `company` or `group`.

## CLI/AI Suggestion Schema

Minimum suggestion object:

```json
{
  "suggested_group_name": "創科集團",
  "members": [
    {
      "company_code": "A001",
      "company_display_name": "創科實業"
    }
  ],
  "confidence": "low|medium|high",
  "evidence": [
    {
      "type": "alias|name_similarity|existing_mapping|report_context|user_target",
      "value": "..."
    }
  ],
  "warnings": [
    "same_name_different_code",
    "insufficient_evidence",
    "brand_or_subsidiary_uncertain",
    "external_evidence_required"
  ]
}
```

## Risks

- Incorrect grouping changes competitive analysis conclusions.
- Same Chinese display name is not enough evidence for confirmed grouping.
- Same Chinese display name is also not enough for a confident CLI/AI candidate unless supported by a seed, user target, or strong internal alias pattern.
- If report scope is implicit, historical charts become incomparable.

Mitigation: confirmed mappings require user action; report scope is explicit; suggestions carry evidence and warnings.
