# Design: 報表契約同步與母體閘門

## §1 為什麼要閘門，而不是「這次修好就好」

同一類錯誤在四天內出現三次（母體沒接）、五個檔同時過期（文件不同步）、
色票從 28 漲到 49。共同特徵是**不會報錯**：

- 母體沒接 → 數字照樣印出來，只是印的是全庫的
- 文件過期 → CLI 照著寫，產出通順但對不上實際報表
- 色票增生 → 圖照樣畫，只是同一個語意在兩張圖用不同顏色

⚠ 靠人記得是無效的護欄——這三件都是我們自己在「記得要注意」的狀態下發生的。

### 閘門判準（沿用 `deepen` design §1.2 三問）

1. 不看語意能不能判定？
2. 🔴 滿足它的**唯一**途徑是不是把事情做對？（恆等式 vs 代理指標）
3. 若有自由度：偏差是**多出來的**（可見）還是**缺席的**（兜不住）？

本 change 的三個閘門逐一過三問：

| 閘門 | Q1 | Q2 | Q3 |
|---|---|---|---|
| `report_key` 集合對帳 | ✅ 集合比對 | ✅ 恆等式：文件提到的 key ⊆ 定義的 key | 偏差是「多出來的」——文件多提一個立刻現形 |
| 母體彙總必須吃 `patent_ids` | ✅ AST 掃 SQL | ✅ 恆等式：直查 DB 的彙總不帶母體＝必錯 | 白名單是**顯式**的，缺席不會靜默通過 |
| 色票唯一定義處 | ✅ 數硬編碼色 | ⚠ 代理指標——數量不增不保證語意正確 | 見 §4 的補強 |

## §2 五個檔的權責邊界

改一次報表要追五份文件，根因是**沒有人規定誰該寫什麼**。先定邊界：

| 檔 | 唯一負責 | 明確不負責 |
|---|---|---|
| `report_definitions.py` | **報表存在性與欄位**（report_key、label_zh、columns、aggregates） | 呈現形式、解讀重點 |
| `prompts/report-narrative-flow.md` | 每個 report_key 的**解讀重點與禁止超譯** | 報表有哪些欄、長什麼樣 |
| `prompts/content_standard.md` | **跨報表**的寫作標準（句型、量詞、證據要求） | 逐 report_key 的指引 |
| `skills/.../SKILL.md`＋`narrative.md` | **投影片**的呈現規則與撰稿範例 | 報表本身的定義 |
| `add-deck-delivery-line/design.md` | deck 的**頁面盤點**（哪些報表上哪些頁） | 報表欄位細節 |

⚠ 邊界的意義：`narrative-flow` 不該複述欄位清單（那是 `report_definitions` 的事），
它只該說「這張圖要解讀什麼、不准超譯什麼」。目前的過期描述有一半是因為它抄了結構。

## §3 母體閘門的白名單設計

不是所有 DB 直查都該吃母體。三種正當的全庫用途：

1. 系統健康檢查（連線、schema）
2. 跨 workspace 的維運統計（不進報表）
3. 詞彙／對照表載入（與母體無關）

因此閘門形式是**顯式白名單**：

```python
# 模組層宣告，缺席即紅
WHOLE_DB_QUERIES = {
    "_fetch_vocabulary": "詞彙對照載入，與母體無關",
    ...
}
```

⚠ 白名單要求寫**理由**不只是函式名——「為什麼這個可以不吃母體」寫不出來，
通常就代表它其實該吃。

## §4 色票：數量不是判準

「不得新增第 29 種」是**代理指標**——它擋不住「把兩個語意塞進同一個色碼」，
也會誤擋「真的需要新語意色」的情形。改成兩層：

- **硬判準**（恆等式）：所有色票必須從唯一定義處取，程式碼中不得出現裸 hex。
  用 AST 掃：`chart_runner` 內的 `"#XXXXXX"` 字面數必須為 0（常數定義區除外）。
- **軟揭露**：色票總數與各自語意列成表，新增時必須在表裡寫用途。
  數量本身只揭露不擋。

⚠ deck 側的 `RGBColor(0x..)` 與 chart 側的 hex 是**兩種寫法同一件事**，
收斂時要跨語法比對，不能只掃 hex。

## §5 家族數與專利類型的落點

### 家族數

| 落點 | 決定 | 理由 |
|---|---|---|
| 封面數字磚 | ✅ 保留（`48 個家族`） | 母體規模的基本描述 |
| 趨勢兩表欄位 | ❌ 移除顯示（rows 保留） | 中間量；`narrative-flow:295` 已要求 CLI 自行查同族判讀 |
| KP 表／KP 象限泡泡 | ✅ 不動 | per-applicant 維度，與封面的 per-workspace 不衝突 |
| 受理局頁註記 | 🔴 修來源 | 現在取自 legacy 全庫表（187），應為母體內數字 |

口徑定死：**`count(DISTINCT "WIPS同族ID")`，母體＝workspace 的 `patent_ids`**。

- 實測欄位形狀：全庫 281 件，多值 0、空值 0（單值乾淨，不需 surrogate）
- 滑雪機 55 件 → 48 族（件/族 1.15）；割草機 226 件 → 163 族（1.39）
- ⚠ 日後若出現缺同族 ID：**各自算一族**，不得併成一族「未知」
  （那會把不相干的案子合併成假家族）

### 專利類型

用詞統一為**設計**（台灣法定用語為「設計專利」，2013 年起取代「新式樣」）。
判定一律走 `transforms/patent_kind.py` 唯一定義處。

⚠ **改名要分類不能盲改**：「外觀」在庫裡有兩種語意——

- **專利類型**（＝設計專利）→ 改名為「設計」
- **產品的外觀／造形**（設計案保護的標的、文獻備註內文）→ **保留**

盲目全域取代會把「設計要點在於產品外觀造形」改成「設計要點在於產品設計造形」，
語意破壞且不可逆。實掃分布：後端 46 處／測試 60／prompt 7／deck 5／OpenSpec 73。
⚠ **OpenSpec `archive/` 底下不改**——那是歷史紀錄。

## §6 封面數字磚

四格，第四格一格三數字：

```
  55          48           4        17·27·11
件專利      個家族      個受理局    發明·新型·設計
                                      專利類型
```

- 四個數字**全部由引擎產出**寫進 `report_data.json`，CLI 只填不算
  （沿用既有 `population`、`patent_kind` 的「一方產生、一方消費」）
- 格數不變 → 無版面容量風險，不需重測 `deck_layout` 裕度
- `stats_note` 的「存活家族」拿掉：四格已有「個家族」，note 再給第二個家族口徑
  只會讓讀者要分辨兩個數的差別

## §7 驗收判準

| 項目 | 判準 |
|---|---|
| 對帳閘門 | 綠；且塞一個假 report_key 進文件要紅（**反向驗證**） |
| 母體閘門 | 綠；且把某個彙總的 `patent_ids` 拿掉要紅 |
| 封面家族數 | 滑雪機 48、割草機 163——**兩者不相等**證明跟著母體走 |
| 封面三分法 | 滑雪機 發明 17／新型 27／設計 11；割草機 151／65／10 |
| 受理局註記 | 數字 ≤ 該 workspace 件數（現況 187 > 55 會被這條抓到） |
| 色票 | 裸 hex 字面為 0；深藍收斂為一；跨 deck/chart 比對一致 |
| 用詞 | 三分法標籤為「設計」；產品外觀語意的「外觀」未被誤改（逐處人工過目） |
| 趨勢表 | 不含家族數欄；`chart_rows` 仍有資料 |
| 回歸 | 三層範圍（直接／整合／契約）＋**符號反查消費者**比對已跑清單 |

## §8 不做什麼

- 不動圖表版型、不改頁面配置（輪二）
- 不重跑 deck
- 不讓 `family_country_layout` 退場（只停止誤用）
- 不處理解讀的**深度**議題（覆蓋率、軸 metadata、樣本門檻——輪二）
