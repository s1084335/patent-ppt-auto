# Design: 簡報漸進預覽與單頁編輯

## 1. 三個開放問題的答案（規格階段實測清空）

proposal 列了三個開放問題。全部**用實測而非推論**回答，結論是它們互相收斂成
同一個設計選擇。

### 1.1 ⏱ 整份重組只要 1.8 秒——「單頁」是編輯範圍，不是重組範圍

實測（`#426` 現成素材 `report_trial_20260819_143341`，18 頁）：

```
make_deck.py content.json png/ deck.pptx svg/   →  1.8 秒
產物：deck.pptx 2,225,829 bytes ＋ SVG 18 頁
```

`deck_layout.build()` 與 `build_svg()` 都是**整份組版**，沒有逐頁介面。
原本擔心「改一頁要不要整份重產 pptx」是個假問題：

| 階段 | `#426` 實際耗時 | 單頁編輯要不要重跑 |
|---|---|---|
| 素材組裝＋機械步 | 約 1 分鐘 | 不用（圖表 PNG 已在磁碟） |
| **CLI 撰稿** | **約 37 分鐘** | **不用**（這是省下的大頭） |
| **目視迴圈** | **約 25 分鐘** | **不用**（使用者裁決） |
| 組版（build） | **1.8 秒** | **重跑全份** |

🔴 **設計選擇：不做 per-page pptx patching。**
「單頁編輯」的「單頁」指**使用者改的範圍**，重組一律整份。

理由：
- 省下的 62 分鐘來自不重撰稿與不重目視，不是來自不重組版
- per-page patching 要維護「哪些頁受影響」的相依圖，而版面本來就有跨頁效應
  （同頁互斥色、結論頁分頁、頁碼）——那張相依圖會是新的漂移來源
- ⚠ 最簡單達到目標的寫法：整份重組，1.8 秒，零相依圖

**可驗證的推論**：只改一頁的 content，其餘頁的 SVG 應**逐位元組相同**。
這是 tasks 的驗收項，不是假設。

### 1.2 閘門不切分——跑全份，理由同上

`check_content` 的六道檢查裡至少三道**本質上需要全份**：

| 檢查 | 為什麼不能只看一頁 |
|---|---|
| `_check_conclusion_coverage` | 涵蓋率 N/M 的分母是全部主題 |
| `_check_cover_stats` | 封面數字對帳的是整份母體 |
| 同頁互斥色（`NOT_SAME_PAGE`） | 「不得同頁」需要看每一頁 |

既然重組已經是全份且只要 1.8 秒，閘門也跑全份——**不為了「單頁」這個詞去切分
一個本來就完整的檢查**。切分會製造「單頁版檢查」與「全份版檢查」兩套判準，
那是本專案反覆在消滅的東西。

### 1.3 SSE payload 只帶頁號與資產路徑，不帶圖

現有管道（`api/events.py`）：thread `LISTEN patent_events` → `asyncio.Queue`
fanout → `yield f"data: {json.dumps(payload)}"`，心跳 15 秒。
payload 直接來自 `pg_notify`。

⚠ **PostgreSQL `NOTIFY` payload 上限 8000 bytes**——base64 一張 PNG 必爆。
故逐頁事件只帶識別資訊，前端據以打既有的 asset 端點取圖：

```json
{"type": "deck_page", "run_id": 427, "version": "report_trial_...",
 "page": 7, "total": 18, "asset": "svg/p07.svg"}
```

⚠ 「total」必須帶：沒有分母的話前端無法顯示「7/18」，只能顯示「已產 7 頁」
——那讀起來像「只有 7 頁」。

## 2. 漸進預覽的推送時機

🔴 **只推機械步產出的頁**（2026-08-20 使用者裁決）。

現行 `_progress(stage, pct)` 在 11 個點回報（`materialize` 5% → `persist` 92%），
但那是**階段文字＋百分比**，沒有頁面。本 change 在 `build_svg` 完成後，
逐頁發出 `deck_page` 事件。

### 為什麼不推目視迴圈的逐輪修改

- 中途看到的都應是**已通過機械閘門**的頁，不給人看半成品
- 目視每輪可能改多頁，逐輪重推會讓同一頁在畫面上反覆變動
- ⚠ 但**跑完要整批更新**：目視改過的頁與機械步版本不同，不更新等於讓使用者
  停在舊畫面上而不自知——那是缺席型偏差

### ⚠ 失敗時的行為（本設計刻意處理）

`#426` 失敗時前面十幾頁已正確組好卻一頁沒被看到。本 change 之後，
**失敗仍保留已推的頁**——使用者至少能看到卡在哪一頁、前面長什麼樣。
故逐頁事件與 job 狀態**解耦**：job failed 不清除已推的頁。

## 3. 單頁編輯的資料流

```
使用者在「匯出報告」頁展開第 N 頁的 content 欄位
   → 送出 {version, page_index, content_patch}
   → 後端合併進 content.json（只改該頁）
   → check_content 全份 ＋ audit_deck        ← 重跑
   → make_deck 全份重組（1.8 秒）
   → 不重撰稿、不重跑目視                      ← 使用者裁決
   → 逐頁事件推回前端
```

### 3.1 為什麼重跑閘門但不重跑目視

| | 守什麼 | 人改了要不要重驗 |
|---|---|---|
| `check_content`／`audit_deck` | **結構與口徑**（動詞白名單、依據紀律、字級白名單、同頁互斥） | **要**——人也可能違反，且秒級零 token |
| CLI 目視 | **AI 撰稿品質**與版面觀感 | 不要——人自己改的不需要 AI 再審 |

⚠ 但版面溢出是例外：`make_deck` 的回傳碼已涵蓋「版面溢出或圖內字級不足」，
那是組版時就算得出來的機械結果，不需要目視。編輯流程必須把這個回傳碼**呈現給
使用者**，不能吞掉——否則人改出溢出的內容而系統不吭聲。

### 3.2 人工編輯必須留痕

⚠ 交付物的證據鏈目前是 audit（查了什麼）＋ content.json（據此寫了什麼）。
人工介入若不留痕，證據鏈會出現**無法解釋的斷點**——日後有人問「這句話的依據
在哪」，audit 裡找不到，而沒有任何地方說明它是人改的。

每次編輯記錄：改前 hash／改後 hash／頁號／時間／`edited_by`。

落點**優先不加 migration**：沿用既有 manifest（已記 content hash）。
⚠ 若 manifest 結構容不下，才考慮 migration——但要在 tasks 明確揭露，
不得為了省事把稽核資訊塞進不相干的欄位。

## 4. 明確不做的事與理由

### 4.1 不引進 ppt-master 的 `svg_editor`

實查（2026-08-20）：

| | 我們 | ppt-master `svg_editor` |
|---|---|---|
| 規模 | — | **5,234 行**（Flask server 1205 ＋ app.js 2792 ＋ css 877） |
| 編輯對象 | `content.json` | **SVG 的標註屬性**（`data-edit-target`／`data-edit-annotation`） |
| 真實來源 | content.json | SVG（它以 SVG 為創作面） |

⚠ 我們的 SVG 是 content.json 的**派生中間物**——編了 SVG，下次重組版就被蓋掉。
它的架構對它自己是對的，對我們是反的。

**值得借鑑的是資料模型不是程式**：把「使用者說這裡要改什麼」結構化存下來給
AI 讀，這個概念可用，但落點必須是 content.json。⚠ 本 change **不做** AI 套用標註
（那是另一條線），只做人直接改。

### 4.2 不引進 `confirm_ui`

實查其檔頭：「Template and Strategist confirmation UI Server (**Steps 3-4**)」
——產製**前**的模板選擇與策略確認，與本 change 的產製**後**預覽編輯無關。

### 4.3 不含窄轉換器接上

`svg_to_pptx.py`（468 行、三種元素詞彙）2026-08-14 封存中。接上與否是獨立決定
（見 `decisions.md` 2026-08-20 更正段），不在本 change 範圍。

⚠ 但兩者有**相依**：若日後接上轉換器，pptx 將由 SVG 派生，屆時「重組全份」的
成本結構會改變（可能更快，因為不必走 python-pptx）。本 change 的設計不阻礙那條路
——因為我們重組的是**全份**，轉換器換上去只是換掉最後一步。

## 5. 風險與已知限制

| 風險 | 處置 |
|---|---|
| `NOTIFY` payload 8000 bytes 上限 | 事件只帶頁號與路徑（§1.3） |
| 前端逐頁取圖造成 18 次請求 | 走既有 asset 端點；圖已在磁碟，非重算 |
| 使用者改出違反口徑的內容 | 閘門全份重跑（§3.1） |
| 使用者改出版面溢出 | `make_deck` 回傳碼必須呈現，不得吞掉（§3.1） |
| 人工編輯污染證據鏈 | 稽核留痕（§3.2） |
| 目視改過的頁與機械步版本不同 | 跑完整批更新（§2） |

### ⚠ 未涵蓋（明文揭露）

- **並行編輯**：兩個人同時改同一版本的不同頁。本版不處理，以「後寫入者覆蓋」
  為預設行為，並在 tasks 揭露。⚠ 不做樂觀鎖是因為目前是單人使用情境；
  這個假設一旦不成立就要重新設計，故寫在這裡而不是埋在程式裡。
- **編輯歷史回溯**：只記最近一次的改前 hash，不做完整版本樹。
- **AI 套用標註**：見 §4.1。
