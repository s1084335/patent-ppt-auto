# Design: HTML 報表版面與章節改版

## 前提：一條限制已經失效（實測）

`chart_runner.py:3729` 與 `decisions.md:3613` 都明訂：

> SVG 內字級寫死 15.1px，顯示字級＝15.1 × (顯示寬 ÷ 原始寬 1180)。
> **要改圖內字就改這個寬度，不要去動 SVG**（動了會連 deck 一起壞）。

**實測 2026-08-21**：

| 檢查 | 結果 |
|---|---|
| `deck_layout.py` | 不存在 |
| `svg_canvas.py` | 不存在 |
| `build_ppt.py` | 不存在 |
| 全庫 `from/import.*deck|svg_canvas|build_ppt` | **0 筆** |
| 殘留的 `deck` 字樣 | 全在註解與 docstring |

⇒ 「不要動 SVG」的**唯一消費者已消失**。使用者 2026-08-21 明確同意 SVG 可改。

⚠ 這條必須先解開，否則本案自相矛盾：

```
維持 SVG 15.1px，要顯示成 16px：
  顯示寬 = 16 ÷ 15.1 × 1180 ≈ 1250px   ← 比原生 1180 還寬
```

「圖內字 16px」與「圖不要太大」在舊機制下**不可能同時成立**。

⚠ 收尾時要一併清掉 `chart_runner.py:3729-3734`、`chart_sizing.py:42-43` 與
`decisions.md:3613-3616` 的舊敘述——**留著就是假知識**，下一個人會照著繞路。

## 一、字級：從「反推」改為「直接設定」

### 現況

```
SVG 內字級 15.1px（寫死）
      ↓ × (顯示寬 ÷ 1180)
.chart-media { max-width: 860px }  →  顯示 11.0px
```

字級與寬度**綁死**：想要字大就得圖大，想要圖小就得字小。

### 改後

```
字級定義處（唯一） ──→ SVG 產生時直接寫入 16px
                  └──→ CSS 的 h1 / h2 / body

圖表寬高 ←── 由資料量決定（與字級無關）
```

兩個維度解耦。這是 EXP-018 的全部內容。

⚠ **字級要有唯一定義處**（EXP-017）：現況字級散在 CSS 與 SVG 產生器兩處，
改版時很容易只改一邊——而 SVG 那邊不會有任何測試變紅。

## 二、圖表尺寸：依資料量伸縮

### 為什麼固定值兩端都錯

| 資料量 | 固定 400px 高 / 860px 寬 |
|---|---|
| 大（類別多、列多） | 擠壓、標籤相黏、看不清 |
| 小（三五個類別） | 稀疏的圖佔滿版面 |

### 伸縮的依據

尺寸由**該圖實際承載的資料量**推導——類別數、列數、標籤長度。

⚠ 既有程式**已經有這種推導**：`chart_runner.py:2194` 的「下限 20px——再低則列標籤
會相黏」就是同一類判斷。本案是把這種推導從「防相黏的下限」擴為「決定整體尺寸」，
**不是新發明機制**。

### 上下界

- **下界**：小資料量不至於縮到不可讀
- **上界**：大資料量不至於無限拉長

⚠ 上下界的取值要記錄**推導依據**（從字級與最小可辨距離反推），不要憑感覺填數字
——憑感覺的常數下次沒人敢動。

## 三、章節與解讀深度

### 承接第二世代的既有定案

`decisions.md:3032`（2026-08-07）：

> 拿掉標籤後格式仍固定（一條數字、一條解釋、一條建議＋「建議進一步檢視 X 以確認 Y」
> 固定結尾）＝**只是換皮**。定案：條數、句式、順序、每條講什麼**都由該頁內容決定**；
> 固定的只有兩個內容要求——**要有數據依據**、**要講得出原因和結論**。

本案不改這條，只是把它從已退場的簡報線承接到 HTML。

### 深度不需要新判準

使用者要的「技術趨勢」深度，既有九把鎖已涵蓋：

| 使用者要求 | 既有鎖 |
|---|---|
| 有數據依據 | 鎖四·至少一條帶統計數字 |
| 講得出成因 | 鎖五·至少一條解釋成因 |
| 具名對象 | 鎖七·整頁至少點到一個具名對象 |

⇒ EXP-022 明寫「由既有品質規則承載，不新增判準」。真正要做的是讓這些鎖
**覆蓋到 HTML 顯示的長文**——那是 `harden-report-narrative` 的 EXP-011，不是本案。

### 🔴 「相對應行動」的陷阱

使用者要的解讀深度是「技術趨勢**和相對應行動**」。前半段如上表已涵蓋；
後半段**不能寫成「每則都要有」**。

`report-professionalism-spec.md` 問題 14：

> 🔴 **這是我們自己造成的**——「建議進一步檢視 X，以確認 Y」是
> `ai_narrative_runner.py:515` 與 `report-narrative-flow.md:221` **硬性規定的固定句型**。

病因鏈是：

```
規定「每頁都要有建議」
      ↓
沒東西可建議的頁也得生一句
      ↓
只能生對任何資料都成立的萬用句
      ↓
每頁結尾都一樣 ＝ 模板化
```

`decisions.md:3038` 當時的收斂是「下一步建議照舊『**有可執行內容才寫**』……**句型不拘**」。

⇒ EXP-023 照這條寫：**有才寫、寫了要具體、不規定句型**。並加一個 scenario
直接禁止萬用句——這是可檢視的性質（能不能互換到其他報表），不是格式。

## 三之二、敘述統計與限制說明的位置（EXP-026、EXP-024）

使用者 2026-08-21 定的閱讀動線：

```
結論          ← 先給答案（BLUF）
敘述統計      ← 這份資料是什麼（新增）
圖表章節      ← 論證
整體限制說明  ← 最後，精簡（「高層也不想看」）
```

### 敘述統計的內容與來源（實測 2026-08-21）

使用者選定五類。**不是全部現成**，兩者要分開看待：

| 內容 | 來源 | 狀態 |
|---|---|---|
| 各專利類型件數（發明／新型／設計） | `fetch_patent_kind_summary` | ✅ 現成 |
| 總件數 | 引擎已供給 | ✅ 現成 |
| 家族數 | `chart_runner.py:115-117` `COUNT(DISTINCT FAMILY_ID_EXPRESSION)` | ✅ 現成 |
| 法律狀態分布 | `transforms/legal_status.py` 四桶＋`STATUS_BUCKET_ORDER` | ✅ 現成 |
| 分群覆蓋率 | 既有 `cluster_section_note` 用的同一組數字 | ✅ 現成 |
| 時間範圍（起訖年） | `application_year` 欄位在用，但**無 min／max 計算** | ⚠ 需新增 |
| 受理局數 | `fetch_cover_stats.jurisdiction_count` | ✅ 現成（2026-08-21 更正：規劃時誤判為需新增） |
| 主題數（本次分群總數） | ⚠ 既有 `topic_count` 是「某申請人涉及主題數」，**語意不同** | ⚠ 需新增 |

⚠ 最後一列是典型的**同名不同義**陷阱：`topic_count` 看起來就是要的東西，
拿來用會得到一個看似合理、實際錯誤的數字——而且不會有任何測試變紅。

⚠ 新增的三項要放進**既有的確定性計算層**，不要寫在 HTML 產生器裡：寫在產生器裡
就沒有第二個消費者能重用，下次有人要同一個數字時又會再算一次。

🔴 **敘述統計 SHALL 消費既有計算，不自行再算一次**。同一個數字出現在兩處就是
兩個定義處——而不一致本身不會報錯，只會在讀者發現「上面寫 216、下面寫 214」時爆出來。

⚠ 專利類型判定只能用 `document_kind`，不能用 `patent_type`：後者的 WIPS 來源欄
只有兩值，11 件設計案會全被歸進發明（`transforms/patent_kind.py` 是唯一定義處）。
敘述統計直接呼叫既有函式即可，**不要自己寫判定**。

### 兩種「限制」必須分開處理

| 類型 | 例 | 位置 | 理由 |
|---|---|---|---|
| **逐圖口徑註記** | 「設計 N 件依文獻種類排除，不列入主題分類」 | ⚠ 留在該圖旁 | 註記離開它說明的數字，那個數字就無法判讀——讀者會問「這 216 件是全部嗎」 |
| **整體限制說明** | 資料涵蓋範圍、時間截點、已知缺漏 | 報表末尾、精簡 | 屬全篇性質，不綁任何單一數字 |

🔴 實作時最容易做錯的是「把所有 note 一起掃到最後」。那會讓每張圖的數字失去口徑。

## 四、穩定性策略：不為「以後會改」預埋抽象

使用者 2026-08-21 明示版面／內容／章節**之後可能再修**。

⚠ 常見的誤讀是「那就做一個設定層，以後好改」。不要。理由：

- 預埋的設定層是**現在就要付的複雜度**，換取一個不確定的未來需求
- 真的要改時，需求形狀多半與預埋的不同，設定層反而擋路
- 專案規則明訂：不為想像中的未來需求預加抽象層

**唯一該做的「為將來準備」是 EXP-017 的唯一定義處**——那不是預埋抽象，
而是消除已經存在的重複（字級現在散在 CSS 與 SVG 兩處）。

## 風險與回復方式

| 風險 | 評估 | 處置 |
|---|---|---|
| 🔴 把「相對應行動」寫成必填，複製第一世代模板化 | **高**。是最直觀的實作 | EXP-023 明訂「有才寫」；驗收判準 12、13 逐則檢視 |
| 改 SVG 字級破壞既有量測基準 | 高，但可預期 | 基準本來就要重建；動工前先記錄現況值作對照 |
| 只改 CSS 沒改 SVG（或反之） | 中。SVG 那邊不會有測試變紅 | EXP-017 唯一定義處；驗收量渲染後實際值 |
| 尺寸伸縮的上下界憑感覺填 | 中 | 取值要記錄推導依據 |
| 為「以後會改」預埋設定層 | 中 | design 四已明訂不做 |
| 舊註解留著誤導後人 | 中 | 程式落點已列出三處要清 |
| 🔴 敘述統計自己算一次，與各章節不一致 | 中 | EXP-026 明訂消費既有計算；驗收判準 10c 逐個數字比對 |
| 🔴 把逐圖口徑註記一起掃到報表末尾 | 中。是最直觀的實作 | EXP-024 明訂留在原處；驗收判準 10d 全篇檢視 |
| 既有報表版面改變造成困惑 | 低 | 只影響新產製；既有版本目錄不變 |

**回復方式**：無 migration、無 schema 變更。revert 後新產製的報表回到舊版面，
既有產出不受影響。⚠ 但**量測基準若已重建，revert 時要一併回復**，否則測試會紅在
與本案無關的地方。

## 未採用的替代方案

| 方案 | 為何不採 |
|---|---|
| 維持「由顯示寬反推字級」，把圖撐到 1250px | 比原生還寬，與「圖不要太大」直接衝突 |
| 圖內字用 CSS 設定 | SVG 內的文字字級不吃外部 CSS——這正是舊機制繞路的原因 |
| 保留固定高度，只調數值 | 兩端問題不變，只是換一組不對的數字 |
| 規定每則解讀都要有行動建議 | 🔴 第一世代模板化的直接成因 |
| 新增「技術趨勢」「行動」固定小標 | 同上；且違反 `decisions.md:3036`「格式完全不固定」 |
| 為將來改版預埋版面設定層 | 現在就要付複雜度，換不確定的未來需求 |
| 拆成「字級」與「章節」兩個 change | 兩者都改 `chart_runner` 的 HTML 產生器與 `chart_sizing`；`decisions.md:3633` 已有先例——分兩次動同一個檔只會製造衝突 |
