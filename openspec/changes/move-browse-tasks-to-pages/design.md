# Design: 瀏覽區作業頁面化

## 現況證據（實測）

### 1. 公司名治理是子系統，不是區塊

前端 `index.html` 中公司名／集團／別稱／正規化相關函式 **共 65 支，
從行 1187 橫跨到 5937**。它承載四段流程：

```
建代碼組 → AI 集團建議 → 待審覆核 → 未歸戶名稱處理
```

目前全部塞在瀏覽頁一個 `details` 收合面板的 `#company-name-block` 裡。

### 2. TW 狀態管理是一份待編名單

`WSP-012` 明訂它「只列出 `country_code='TW'` 且 `legal_status` 空白的專利」，
逐筆選值儲存後從清單移除。這是典型的「待辦名單」形狀。

### 3. 文獻備註不是名單

瀏覽頁的文獻備註只有：覆蓋率提示（`#note-coverage`）＋ 一顆「產文獻備註」按鈕。
沒有名單要編、沒有逐筆操作。

**決策**：只搬前兩者。搬文獻備註會讓使用者為了按一顆鈕多跳一頁。

### 4. 「有頁面、無導覽項」已有前例

案件比對：`renderComparison()` 存在、`renderMain()` 的 `switch` 有 `case 'comparison'`、
後端 `/api/comparison` 與 8 支測試全在，**但左導覽沒有按鈕**——2026-08-03 使用者
「案件比對區塊先移除掉」時只收了入口。

原始碼註解明載恢復方式：「在此加回一個 nav-item 按鈕，`data-nav` 與 `onclick`
皆指向 comparison」。

**決策**：沿用此模式，不發明新機制。

### 5. 待辦數的權威端點已存在

- 未歸戶名稱：`company_aliases.count_pending_names_for_patents`
- TW 待登錄：`patent_queries.list_pending_tw_legal_status_patents`

**決策**：入口數字一律取自這些端點。前端自數會產生第二份計數邏輯，而兩份必然漂移
——本專案已反覆踩過。

### 6. `company-governance` 規格未綁定介面位置

該 spec 的 21 條需求（CMP-001 ~ CMP-021）**沒有任何一條規範它要放在瀏覽介面**。

→ 公司名治理搬頁**不需要 spec delta**，因為沒有行為規格會變。
→ 只有 `WSP-012` 明文寫「在專利瀏覽介面提供預設收合的區塊」，必須 MODIFIED。

⚠ 這個差異是查出來的，不是假設的：若沒查就一起寫 delta，會憑空修改一份不需要動的規格。

## 搬遷手法

**只改掛載點，不動函式本體。**

```
現在：renderBrowse() 產生 details > #company-name-block
              ↓ 內部呼叫
      renderCompanyCodeRegistry() / renderCompanyGroupRegistry() / …（65 支）

改後：renderCompanyGovernance()  ← 新頁的進入點
              ↓ 呼叫同樣那 65 支，不改它們
      renderCompanyCodeRegistry() / renderCompanyGroupRegistry() / …
```

`renderBrowse()` 只留入口卡片與待辦數。

⚠ 若發現非改函式本體不可才搬得動（例如函式硬編了 `#browse-body` 這類宿主 id），
那代表耦合比表面深。**停下來重新評估，不要硬拆**——硬拆的結果會是「搬完之後某個
邊角功能靜默失效」，而純搬遷的驗收判準（行為等價）恰恰最難察覺這種失效。

## 入口卡片

輪一（`add-prefilter-negative-keywords`）已建立第一個入口。本 change 將其抽為共用元件，
三個入口共用同一份：

```
┌── 作業入口 ──────────────────────────┐
│ 初階篩選      關鍵字 3 組·待裁決 12 → │   ← 輪一建立
│ 專利權人治理  未歸戶 8 筆          → │   ← 本 change
│ TW 專利狀態   待補 15 件           → │   ← 本 change
└──────────────────────────────────────┘
```

⚠ 抽共用元件是**本 change 的責任**而不是輪一的：輪一只有一個入口，當時抽象化沒有
根據；三個才看得出共同形狀。過早抽象與過晚抽象都有成本，這裡選在有三個實例時做。

## 風險與處置

| 風險 | 處置 |
|---|---|
| 純搬遷的行為差異最難察覺 | 判準 1 要求逐項對照搬前搬後的輸出，不接受「看起來一樣」 |
| 65 支函式互相呼叫，耦合可能比表面深 | 只改掛載點；若非改本體不可則停下重評，不硬拆 |
| 既有前端靜態斷言會紅 | 改斷言可以、降低要求不行；每處改動註明理由 |
| 兩塊同時搬，壞了難歸屬 | 切片 B、C 各搬一塊，各自獨立驗收 |
| 待辦數與後端不一致 | 一律取自權威端點，並以測試斷言前端不自數 |

## 未採用的替代方案

| 方案 | 為何不採 |
|---|---|
| 加左導覽項 | 使用者裁決：先照無導覽項做，用過覺得繞再加 |
| 連文獻備註一起搬 | 它沒有名單要編，搬了只是多一次跳頁 |
| 順便重構那 65 支函式 | 重構與搬遷混在一起，出事無法歸屬。要重構應另開 change |
| 一次把兩塊都搬完再驗收 | 壞了分不出是哪一塊；改為各自獨立切片 |
| 在輪一就抽共用入口元件 | 當時只有一個實例，抽象沒有根據 |
