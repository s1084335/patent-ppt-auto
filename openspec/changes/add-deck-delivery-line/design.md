# Design: 簡報產製接進系統（add-deck-delivery-line）

## Context

skill 九步（2026-08-12 實掃）：①intake ②plan_deck ③chip 重排 ④fit 轉 PNG
⑤撰稿 ⑥check_content ⑦make_deck ⑧audit_deck ⑨COM 轉圖目視。
①–④、⑥–⑧是純機械腳本（uv 一行跑）；⑤是唯一 AI 判斷步；⑨依賴 Windows Office。
既有 AI 通道：Companion 領 job → runner 組 prompt → headless CLI → 驗證回存
（`ai_narrative_runner` 模式）。

## Decisions

### 1. runner 驅動機械步、CLI 只接撰稿（接口的核心形）

```
ai_report_deck_runner（Companion 內，host-agnostic）
  1. materialize_version（沿 narrative 既有函式）→ 版本目錄
  2. subprocess：assemble_from_version → plan_deck →（標記則 chip 重排）→ fit
  3. build_prompt：plan.json＋report.json 素材路徑＋撰稿契約
     → headless CLI → 產 work/content.json（唯一輸出檔，同 narrative 權限面）
  4. subprocess：check_content → 組版（`make_deck`／python-pptx）→ audit
     → **逐頁轉圖**（COM，`pptx_to_png.py`；2026-08-13 起沿用現有工具，見 4-0）
  5. 🔁 CLI 目視迴圈（見下）：CLI 看逐頁 PNG → 有問題修 content.json
     → runner 重跑 4 → 再看；通過或達上限為止
  6. 回存：pptx＋逐頁 PNG 寫 <DECK_ARTIFACT_ROOT>/<version>/，manifest＋紀錄寫 DB
```

**目視迴圈＝現行開發流的「看了回去調」原樣搬進產線，只換工具**
（2026-08-12 使用者明示保留）：開發流是我目視 COM 轉圖後回頭調整再轉再看；
產線由撰稿 CLI 對 **Chromium 逐頁截圖**做同一件事（B 案下截 SVG＝截成品）
——檢查清單沿用 skill 現行目視
清單（重疊、裁切、圖內字可讀、版面平衡、行首標點），發現問題**只能改
content.json**（縮寫、改寫、拆頁、轉純文字頁——與今天人工調整的合法動作
一致；圖表、版面引擎、字級規格照授權界線不得動），runner 重組版重截圖後
再看。**迴圈上限＝產線參數，不沿 skill 開發紀律**（2026-08-12 使用者定案
「產品的不要沿用，改成產線參數」）：skill 的「同一問題最多修兩輪」是
開發時人機協作的停損（修不動就停下來找人談），出處為專案 AGENTS.md
「Token 節制」試行條款；產線語意不同——上限到了＝job failed＋使用者按重產，
故改為可調參數 `DECK_VISUAL_LOOP_MAX_ROUNDS`（env／設定，**預設 4**，
調整不改程式）。達上限即 job failed 並附最後一輪的目視發現。
check_content 的閘門紅走同一個迴圈、吃同一個參數，不另設第二條重試路。

**預設 4 的依據**（2026-08-12 使用者定案，回顧開發實績後定）：開發側交付
`_v17` 走了十幾輪，但其中大半是**版面引擎調整**（字級、斷行估算、撞版）與
**規格層來回**——前者 B 案已從根消滅（斷行寫死＋Chromium 實測 BBox）、
後者已定案凍結，兩類都不落在產線迴圈裡。
⚠ 2026-08-13 這條依據曾隨 B 案撤銷而失效，**第 3 次裁決恢復 B 案後重新成立**
（4-0 沿革）。它仍是產線參數（改設定不改程式），實跑後依目視迴圈紀錄校準。產線迴圈只扛**純內容輪**
（縮寫、改寫、拆頁），該類實績約 2–4 輪：首輪抓大問題、次輪掃殘留、
三輪多為確認。取 4 留一輪餘裕救「差一口氣」，又不致把「撰稿方向錯了」
磨成半成品。每輪成本＝機械重組版（秒級）＋看一批 PNG，遠低於 fail 後
使用者整份重產。⚠ 實跑後依累積數據調參，不改程式；**每輪都要落進
目視迴圈紀錄**，才有數據可回頭校準這個值。

為什麼不讓 CLI 一路跑到底：那需要給 CLI 跑任意 uv 腳本的 Bash 白名單
——權限面等於開發機 agent，與「CLI 只輔助、不碰執行面」的架構原則相反；
機械步本來就是確定性程式，讓 runner 跑還能拿到結構化 exit code 當閘門。
skill 的「自主執行」章節在產品側由 runner 具體化，開發側手動流程仍照 SKILL.md。

### 2. 撰稿契約＝skill 第 5 步的機器可驗形

CLI 輸入：`plan.json`（頁序、structure_checklist、骨架頁）＋`report.json`
（texts／tables／notes）＋narrative.md 寫法規範（隨 skill 遷入產品 repo，
runner 以路徑注入 prompt，與 narrative 線的 prompts/ 同模式）。
CLI 輸出：`content.json` 一檔。驗證：check_content 既有閘門（佔位符未清、
字數、裸數字、措辭）就是撰稿的 contract validator——不另寫第二套。

**取證通道保留（2026-08-12 使用者明示「不能擋掉」）**：撰稿 CLI 配備
**唯讀 MCP 資料庫取證工具**——與 `ai:narrative` 線完全同級（沿 2026-08-09
「取證通道統一走 MCP」與 2026-08-10「代表專利走 CLI 自行查」定案）。
競爭者構型頁顆粒度不足時，CLI 依 plan.json 的 `claim_lookup`（patent_ids）
自行查請求項原文；skill 的四條硬規則（只讀不寫、只補敘述不補統計、
新名詞標來源專利號、斷言範圍＝證據範圍）進撰稿 prompt 原樣約束。
權限面＝「讀素材＋唯讀 MCP 取證＋寫一檔」＝narrative 現況，仍不需 Bash 白名單。
（`fetch_claims.py` 留在 skill 供開發側手動流程用；產品側取證走 MCP，不跑腳本。）

### 3. 產物落點（2026-08-12 定案的實作形）

- `DECK_ARTIFACT_ROOT` 環境變數（沿 `MODEL_ARTIFACT_ROOT` resolver 前例）；
  正式＝NAS 掛載點，現階段＝本機目錄。DB 只存相對 key。
- DB：`workflow_runs`（job 本體）＋`workflow_outputs`（manifest：
  based_on_version、pptx 相對 key、SHA-256、大小、閘門摘要、
  是否經逐頁目視）。**不進 report_artifacts**（那是版本內容資料；
  deck 是衍生交付物，混放會讓版本目錄語意變髒）。
- **過程紀錄一併回存（2026-08-12 使用者指出規格缺口）**：narrative 線的
  取證 audit（8 欄 JSONL）已隨 job 落 DB，deck 線比照——
  ①**撰稿取證 audit**（同一條 MCP 通道自帶，reset-per-task）
  ②**目視迴圈紀錄**（每輪：發現了什麼、改了 content.json 哪裡）——
  失敗路徑本就要求「附最後一輪目視發現」，成功路徑同樣留全程，
  「這份 deck 的每段話查了什麼、改過幾輪」才可回放。
- 失敗不落半成品：pptx 先寫 work dir，全閘門過才搬進 ROOT。

🔴 **2026-08-13（第 3 次裁決）：PowerPoint 與 `comtypes` 移出本表。**
B 案恢復後目視走 Chromium 截 SVG，產線不需要 Office——**不需授權、不需互動桌面

🔴 **唯一不能只靠「裝好軟體」解決的條件**

**CLI 的 PATH 與認證，在服務身分下與互動式登入不同。**
`cli_gateway._CLI_SPECS` 的 `"binary": "claude"` 靠 PATH 解析，而開發機實測
它裝在**使用者 profile 底下**（`C:\Users\user\.local\bin\claude.exe`）——
服務身分的 PATH 通常不含該目錄，且 CLI 的登入憑證也綁使用者 profile。
若解不到，需改為以絕對路徑設定或指定服務執行身分。
⚠ **部署驗收必須實跑一次 CLI**，不能只確認二進位存在。

### 4-0c. 目視截圖的解析度（2026-08-13 實測後補）

**問題**：CLI 讀 1280×720 的全頁圖能判斷溢出、重疊、裁切、對齊（當日實測
`regression_baseline` slide02／slide04 確認），但 SKILL.md 對**行首標點**明訂
「全頁縮圖看不出來，眼睛會自動把標點讀回上一行，要放大到 2× 以上看」——
那條限制對 CLI 同樣成立。目前規格只寫「看逐頁 PNG」，沒說多大張。

🔴 **不預先寫死數字。** 這一節只定三件事：怎麼推導、由誰定義、怎麼驗。
⚠ 直接拍一個「1920」寫進 skill／runner／規格三處，就是上一世代那種
「同一份知識多個落點 → 各自演進 → 不一致不會報錯」的錯法。

1. **判準是能力，不是像素**：目視截圖的解析度要滿足「CLI 能辨識行首中文標點」
   ——那是檢查清單裡最細的一項，過得了它，其餘（溢出／重疊／裁切）必然過得了。
2. **值由 `deck_layout` 導出，不由 runner 自訂**。它已經是版面幾何與字級的
   唯一定義處（`budget()`／`label_page_fit()` 同款），知道投影片尺寸與內文字級，
   截圖倍率就該從那裡推。runner 只消費，不自己算。
3. **⚠ 不是越大越好**：CLI 讀圖有 token 成本，而目視迴圈每輪都要讀一整份。
   要找的是**最小可用值**，不是安全起見開最大。
4. **驗法**（映射校驗時一併做，見 tasks 2.3）：造一頁**刻意植入行首標點**的樣本，
   由低到高試解析度，取「CLI 能穩定指出該問題」的最小值。
   ⚠ 判準是**抓得到**，不是「看起來比較清楚」——後者無法收斂。

**B 案在這裡有個附帶好處**：截的是 SVG（向量），可任意倍率 rasterize 而無損；
COM 轉圖的 `width` 是固定參數，放大會失真。所以解析度這件事在 B 案下是純粹的
成本取捨，不是畫質取捨。

### 4. 組版輸出層＝B 案（2026-08-12 定案；08-13 撤銷後**當日恢復**，見 4-0 沿革）

⚠ 本節內容自 08-12 起未變，中間曾標記為「撤銷、保留供追溯」——第 3 次裁決後
恢復為現行方案。以下為原文：

⚠ 保留追溯——若日後精準度成為實際痛點，這是已經評估過的方案，
不必重新研究一次。

精準度流失的唯一來源是「PowerPoint 保留排版決定權」（原生文字框開檔時自行
換行——估算器猜、COM 驗、08-02 實證連 COM 都與實機有微差）。B 案把決定權
全收回引擎：

```
deck_layout 幾何引擎（原樣）→ 每頁組 SVG（文字逐行斷好、絕對定位）
  → Chromium 量測實際 BBox（取代估算）＋逐頁截圖（＝產線目視，Linux 原生）
  → 窄 SVG→DrawingML 轉換器 → 原生 PPTX（逐行文字定位寫死、關 wrap）
```

- **窄**是關鍵：只支援本 skill 的元素詞彙（矩形卡、逐行文字、圖片、線），
  五種頁型（封面／圖表頁／文字頁／標籤頁／路線圖），不支援 SVG 標準全集。
- PPTX 內文字仍是原生可編輯，但行斷點固定（改長會溢出）——ppt-master 同款取捨。
- **開發期一次性映射校驗（Windows 開發機）**：五頁型逐一
  「Chromium 截圖 vs COM 轉圖 vs 實機開檔」三方對照，映射成立後固定；

  ⚠ 2026-08-13 更正：原文寫「產線（Linux）零 Windows 依賴」——deck 定為
  Windows 版後（見 4c-1a），該句不再是選型論據；B 案的理由只剩精準度。

  截成品），兼作前端 deck 紀錄的逐頁預覽。

#### 4c-1. 🔴 WSL2 實測結論（2026-08-13）：寬度可跨 OS 信賴，**高度不可**

環境備妥後在 WSL2（Ubuntu 24.04）與 Windows 各量一次同一段 SVG 文字
（`Noto Sans TC` 15.1px，同一個 `NotoSansTC-VF.ttf` 檔案）：

| 量的東西 | Windows | Linux | 判斷 |
|---|---|---|---|
| 寬度（每字/em） | 1.0000 | 1.0000 | ✅ **完全一致**，中文全形字寬＝字級 |
| 高度（h/em） | 1.444–1.467 | 1.182–1.222 | ❌ **差約 21%**，且各自有 ±1.5% 抖動 |

⚠ **不是 Chromium 版本問題**：兩邊都對齊到 chromium-1234（151.0.7922.34）後
差異依舊。根因是 OS 字型引擎——Windows 走 DirectWrite、Linux 走
FreeType/HarfBuzz，對 ascent／descent／line gap 的解讀本就不同。
⚠ **也無法用固定係數校正**：比例隨字級在 1.44–1.47 與 1.18–1.22 間各自抖動
（整數像素捨入），不是穩定倍數。

**原定案（跨 OS 前提下）**：`getBBox` 只採信 `width`，`height` 一律由排版
公式算；`overlaps()` 改「橫向量測、縱向推導」；`LS_RENDER` 重量在 Linux 做。

#### 4c-1a. 🔴 上述約束**撤銷**——deck 只做 Windows 版（2026-08-13 使用者定案）

使用者定案「**我們做 Windows 版就好**」。deck runner 本就跑在 Companion 內
（§1），Companion 裝在使用者的 Windows 機器上——量測端與產線端**同一台機器、
同一個 OS**，跨 OS 不一致的前提整個消失。

| 原本被跨 OS 差異擋住的事 | Windows-only 後 |
|---|---|
| `getBBox().height` 不可信（跨 OS 差 21%） | ✅ **可用**。量與跑同一個字型引擎（DirectWrite），只剩 ±1.5% 的整數像素捨入抖動——那是既有程式一直在承受的量級 |
| `overlaps()` 必須改成橫向量測、縱向推導 | ✅ **不必改**（tasks 2.2a 撤銷）。w／h 都吃量測值即可 |
| `LS_RENDER` 重量必須在 Linux 做 | ✅ 改在 **Windows** 做——開發機即產線環境 |
| 映射校驗要「WSL2 截圖 vs COM 轉圖 vs 實機」 | ✅ 三端全在 Windows，量測端本來就統一 |

⚠ **4c-1 的實測數字不刪**：它是「若哪天要上 Linux 產線，這些常數全部要重量」
的憑據。要恢復跨 OS 支援時，本節的四條約束原樣復活——不是重新研究一次。
⚠ **本節不改 B 案的成立理由**：B 案是為了把排版決定權從 PowerPoint 收回
（精準度），不是為了脫離 Windows。「零 Windows 依賴」自此只是副產物，
不再是選型論據。

### 4d. 字級目標與「HTML 圖尺寸 → 投影片字級」的連動（2026-08-12 使用者定案）

**目標字級**（使用者定）：標題 **24pt**、內文 **16pt**、**圖表字 14pt**。
前兩者是組版原生文字，`deck_layout` 已寫死達標；圖表字是 SVG 被縮進圖框後的
**最終顯示大小**，由下式決定。

🔴 **關係式（實測三張圖全部吻合，2026-08-12 依 deck_layout 幾何推導）**：

```
投影片圖內字級(pt) = SVG 字級(px) × 316.8 ÷ SVG 高度(px)
316.8 = 單圖頁圖區高 4.68in 扣邊距後 × 72
```

⚠ **只有 SVG 高度會影響 PPT，寬度不會**（反直覺，但圖是被圖區**高度**卡住的：
圖越扁 → 拿到的寬度越大 → 縮放比越高 → 字越大；寬度只在圖扁到撞滿版
`CW=12.333in` 時才成為限制）。實測現況：

| 圖 | SVG | 圖內 15.1px | fit 上限 20px | 要 14pt 需 |
|---|---|---|---|---|
| 年度趨勢 | 1180×**560** | 8.5pt | 11.3pt | 24.7px ✗ |
| 申請人排名 | 1180×**475** | 10.1pt | 13.3pt | 21.0px ✗ |
| 公司×國家 | 1074×**424** | 11.3pt | 14.9pt | 18.7px ✓ |

**⚠ 14pt 目標在現況幾何下多數達不到**（現況 8.5–13.3pt）。達標條件：
`SVG 高度 ≤ 22.6 × 圖內字級`——fit 放到 18px 時，高度須從 560 降到 **≤407px**。
🔴 **落點＝B 案動組版層時一併定**（圖區幾何與 SVG 高度同時算，見 tasks 2.2c）；
14pt 寫成**驗收判準**，不是事後量出來的數字。

**改「報表種類」那邊的圖尺寸會怎麼影響簡報**（使用者提問，記為契約）：

| 改什麼 | 對 PPT 的影響 |
|---|---|
| `WEB.canvas_width`（1180） | **無影響**（除非圖扁到撞 12.333in 滿版） |
| `WEB.canvas_max_height`（560）或 `row_height` 撐高 | **反比直接影響**——高度減少則投影片字變大 |
| `WEB.data_target_pt`（15px） | 由 deck 的 fit 步驟重新解算，理論上被吸收 |

🔴 **但 fit 有個兩處落點的漏洞**：`fit_render_charts.BASE_FONT = 15.1` **寫死**，
它假設報表圖原字級恆為 15.1px。改了 `chart_sizing.WEB.data_target_pt` 而沒改它，
`bump()` 的倍率就算錯，**不會報錯、只會字級偏掉**。收斂為從 `chart_sizing` 讀取
（tasks 2.2c），並加一致性測試。

### 7. 內容架構吸收批次（2026-08-12 使用者逐項裁決）

從 ppt-master 與比較分析吸收的內容能力。**全批共用同一組護欄**（見 §7.0），
逐項只記落點與理由；⚠ 一律不得寫成「什麼情況必須用什麼」的條件規則
——那是上一世代把判斷寫死、規則互相打架的死因。

#### 7.0 三分法護欄（本批的判準，不是建議）

| 性質 | 落點 | 例 |
|---|---|---|
| 可計算 | **機械寫死**（引擎產、閘門驗） | 來源行、口徑頁、集中度指標、動詞表 |
| 資料裡有線索的取捨 | **判斷留活給 CLI** | 用不用插圖、哪個主題該怎麼解讀 |
| 有時適用的結構 | **選項**（版型可選用，不寫觸發條件） | 三欄帶、圖形文法元件 |
| 寫法傾向 | **建議形**（進撰稿 prompt，不進閘門） | narrative.md 範式 |
| **外部事實**（資料裡沒有線索） | **留給使用者，不留給 CLI** | 受眾、語氣、收件對象 |

⚠ 最後一列是本批新增的分辨（2026-08-12）：**判斷能留給 CLI 的前提是
「資料裡有線索」**。受眾這類 CLI 只能瞎猜的事，不得偽裝成 AI 判斷。

#### 7.1 來源行（機械）

每頁角落標「資料來源：<version>／<report_key>」，引擎印，CLI 不參與。

#### 7.2 三欄分析帶（選項版型）

「現況／驅動／含義」三欄結構作為**可選用版型**，CLI 依內容選用；
不得寫成「趨勢頁必須配三欄帶」。§7.5 的綜合結論頁即其應用。

#### 7.3 narrative.md 寫法範式（建議形）

「先結論後證據」等寫法規範隨 skill 遷入，以**建議形**進撰稿 prompt；
不進 check_content 閘門——寫法是傾向，不是可機械判定的對錯。

#### 7.4 插圖＝參數化圖形文法（機械渲染＋判斷選用）

**不建成品素材庫**（使用者否決：「存哪＋永遠趕不上資料」）。引擎提供
關係型參數化元件，初版六型：流程、循環、對比、階層、並列、時間線。
CLI 在 content.json 宣告 `{"type": "flow", "nodes": [...]}`，引擎確定性渲染
（風格／字型／配色隨 deck 主題）。組合活、渲染死。
⚠ 第一版**不開後門**：不允許 CLI 自由畫 SVG 嵌成圖片——口一開，風格與
品質只剩目視迴圈兜底，四輪不夠用。文法不足時以實例擴元件型，走 openspec 留痕。
閘門：type 在文法內、節點數與文字長度在版型容量內、不撞版。

#### 7.5 資料口徑頁（引擎供權威文字＋CLI 編排可讀性）

ppt-master P3 的「怎麼讀數字」頁——申請件數／現存有效／存活家族／IPC／CPC
母體、共同申請不可相加、家族品質缺口、AI 建議與人工核准比例。
定位＝「來源行」的加強版：先講清楚每張圖在量什麼，後面的圖才不會被誤讀。

**兩層分工**（2026-08-12 使用者修正「可以從引擎生，但還是要經過 CLI，
因為可讀性對於引擎不一定能判斷」）：

| 層 | 誰做 | 內容 |
|---|---|---|
| 口徑事實包 | **引擎**（機械） | 每條口徑的**定義原文＋數值**，來自 `REPORT_DEFINITIONS`、RPT-003／RPT-004 與 DB 統計 |
| 編排 | **CLI**（判斷） | 挑哪幾條上頁（版面容量有限）、排序、下標題、必要時補一句白話說明 |

🔴 **機械護欄：定義文字與數字不得改寫**。閘門逐字比對——頁面上每條口徑的
定義字串必須與引擎供給的原文相符、數值必須與事實包相符。CLI 能選、能排、
能加註解，**不能重寫定義**。這是「CLI 不改圖」紀律的文字版。

⚠ 為什麼護欄非有不可：口徑早已是後端唯一來源，讓 CLI 自行重述＝同一份知識
的第二個落點——後端口徑改了、簡報還印著舊說法，**而且不會有任何東西報錯**。
引擎供文字＋逐字閘門則改一處兩邊同步，同時把可讀性留給看得懂版面的 CLI。

#### 7.6 低件數兩種成因＝集中度指標（機械算）＋解讀（CLI 寫）

「集中持有 vs 分散待驗」的分辨可計算：主題內申請人集中度（件數少且單一
申請人持有＝集中持有；件數少且多家各一件＝分散待驗）。**引擎多產一個
集中度欄位**，CLI 據此寫解讀。機械算數、CLI 說話，兩邊都不越界。
⚠ 雙通道（技術／功效）本系統早已具備（BERTopic 兩條），非吸收項。

#### 7.7 結論頁＝綜合版（2026-08-12 使用者裁決「有沒有結合兩種的綜合版」）

ppt-master P2（專利部要做什麼）與 v17 P2（研發往哪走）**不做二選一**：
兩者共用同一份底層判斷，差別只在同一個發現對誰說成什麼行動。

- **形**：一頁、一主題一列、三欄——**發現**（機械填：密度／成長／集中度／
  家族狀態）｜**研發意涵**（CLI）｜**專利行動**（CLI）。版型＝§7.2 三欄帶。
- **護欄一條沒破**：兩欄都自同一份確定性指標推出，**不需要知道受眾**
  ——「受眾」那題（§7.0 末列的外部事實）在此直接消失，不必動用。
- 🔴 **專利行動欄用有限動詞表**（機械）：佈局／追蹤／迴避設計／細讀比對／
  暫不投入。CLI 只能選不能自創——避免 AI 寫出「應立即提出申請」這類
  法律或商業承諾（越過「AI 只輔助、不做正式決策」的界線）。
- **粒度＝主題層級**；案件層級（境外前五、追蹤某案）歸 §7.8，兩頁不重疊。

#### 7.8 逐案細讀清單＝roadmap 頁**改版**（不新增頁）

ppt-master 的「Priority 1–4＋每項判準」比時間軸有用（看得到「為什麼是這件」）。
依專案規則「刪 > 改版 > 新增」，**把現有短期／中期／長期 roadmap 頁改版**
成「優先序＋判準」形，不並存兩頁——兩頁並存＝同一問題答兩次。

- **候選池機械**：機會矩陣高象限、比對高相似度、家族缺口，引擎算出並排序。
- **取哪幾案、判準怎麼寫**＝CLI 判斷（資料裡有線索）。
- 粒度＝案件層級，與 §7.7 主題層級分工。

#### 7.8b 申請人年度矩陣改**跨度圖**；主題演進**留泡泡**（2026-08-12 使用者裁決）

借鑒 ppt-master「申請人布局・投入節奏」的甘特式跨度條。兩張同型的逐年泡泡
矩陣，只有一張適合換——**判準是「跨度本身有沒有資訊」，不是稀疏度**
（兩張都稀疏）。實測 `report_trial_20260812_133901`：

| 圖 | 列數 | 跨度範圍 | **平均佔全軸** | 裁決 |
|---|---|---|---|---|
| 申請人年度矩陣 | 10 | 0–5 年（4 列為單點） | **11%** | ✅ 改跨度圖 |
| 主題演進——技術主題 | 5 | 2–15 年（1 列跨滿全軸） | **56%** | ❌ 留泡泡 |

- 申請人畫成跨度條＝**錯落短棒**，誰早誰晚、誰只打一槍、有無世代斷層一眼可辨。
- 主題畫成跨度條＝**全部糊成等長**（56%，含一條滿軸），零區辨力。
- 🔴 **本質差異，非本批資料的偶然**：申請人是組織，有明確進場／退場；主題是
  聚類標籤，只要該技術持續有人做就一直有件數，跨度必然接近全軸。換一批專利，
  申請人跨度變長仍是訊息（持續投入 vs 短打），主題則恆滿——**申請人用跨度圖
  安全，主題用跨度圖必壞**。
- ⚠ **不得寫成「平均跨度佔比 <20% 就用跨度圖」的條件規則**（§7.0 禁令）：
  兩張圖各自**定型**，因為決定它的是資料的本質特性，不是每批會變的東西。

**實作要點**：
- 走**改版**（「刪＞改版＞新增」）：泡泡矩陣直接改為跨度圖，兩種畫法不並存。
- **Top 10 與第 11–20 名兩張可併成一張**（跨度條一張放得下 20 列）——省一張圖。
- **保留件數**：`chart_rows` 既有 `total` 欄，條末標總件數；「哪年是高峰」由
  年度趨勢圖回答整體。
- **強調與標記走宣告，不破「CLI 不改圖」**：條的位置與長度＝機械（資料）；
  哪幾條要 highlight、世代分界線畫在哪年＝**CLI 在 content.json 宣告**
  （`highlight: [...]`、`marker: {year, label}`），引擎照宣告渲染。
  CLI 選、引擎畫——與 §7.4 圖形文法同一個形。
- ⚠ **單一來源連帶**：此圖 HTML 報表共用，改版後兩端一起變（unify 定案的必然）。
- 落點＝報表引擎（`chart_runner` 新渲染函式＋`report_definitions` 圖型改宣告），
  deck 只是消費者；掛在本 change 一起做（動機來自簡報品質）。

**主題演進的加強方向另走一路**：其 `chart_rows` 已有 `early_count`／
`recent_count`／`concentration_early`／`concentration_recent`／`status`
（引擎早算好早期 vs 近期消長），**但圖上完全沒用到**——讀者得自己從泡泡大小
推。加強＝把這些標上去（如列末「近期集中↑」），同樣走「引擎算、CLI 宣告
要不要標」，**不是換圖型**。

#### 7.9 IPC/CPC 四張圖用幾張＝機械列候選、CLI 判斷（**現行設計，記入規格防退化**）

使用者提問「IPC/CPC 4 階 5 階加起來四張圖，怎判斷用幾張」。實查現行三層：

| 層 | 誰 | 行為 |
|---|---|---|
| 後端門檻 | 機械 | 4 階 distinct **< 3 種** → 該 report **整個不進簡報**（`CLASSIFICATION_MIN_DISTINCT_L4=3`，2026-08-05 定案；判定寫進 metadata，網頁報表照產） |
| plan_deck | 機械 | 偵測「同一指標多階層」（`_L\d+$` 正則）→ 把候選圖列進 `plan.json` 的 hints 與 `structure_checklist`，**要求判斷** |
| 撰稿 | **CLI** | 看判讀原文決定：分類種類夠不夠分頁；不夠就只留最有訊號的一張、其餘轉判讀文字收成一頁 |

四張圖＝IPC 與 CPC **兩個家族各觸發一次**收頁判斷（同章節只點名一次），
CLI 可決定 4 頁／2 頁／1 頁加文字。

🔴 **不得改回機械門檻**——`plan_deck.py` 註解記著踩過的坑：試過用**表格列數**
當「分類種類多不多」的代理值，實測 IPC 章節表 12 列但 subclass 只有兩種，
判斷全錯。原文：「與其留一個猜錯的門檻，不如在需要判斷的地方要求判斷，
並把候選圖直接列出來。」此即 §7.0「資料裡有線索的取捨→CLI 判斷」的實例，
且是**踩坑後才改成這樣**，日後不得為求「自動化」再加門檻回去。

## Test Strategy

- runner 單元：機械步編排（subprocess 以假腳本樁測順序與失敗短路）、
  manifest 形狀、失敗不落 ROOT。
- 內容架構批次（§7）：口徑頁**定義文字逐字**與數值皆與引擎事實包相符
  （**同一份知識單一落點**的一致性測試，CLI 改寫定義須紅）、集中度指標
  邊界值、專利行動動詞表白名單（表外動詞須紅）、圖形文法 type 與容量閘門、
  綜合結論頁三欄齊備。
- 契約：AI_JOB_TYPES 收錄、前端 mapping（既有跨層測試自動強制）、
  按鈕與紀錄區字面契約。
- E2E（組合驗收）：真版本走完整鏈＋系統 vs 手工逐頁對照。

## Risks

- 撰稿品質退化（headless vs 互動）：Acceptance Gate 3 的對照驗收把關；
  check_content 的措辭／字數／佔位符閘門是底線。
- deck 一跑數分鐘：沿 narrative 的 keepalive／誠實進度模式回報 stage。
- 修正輪數上限：閘門紅 → runner 把 check_content 輸出回饋 CLI 重撰稿，
  達 `DECK_VISUAL_LOOP_MAX_ROUNDS`（產線參數，預設 4）即 failed
  ——上限是可調參數，不再綁 skill 開發紀律（2026-08-12 使用者定案）。
