### 🔴 6.0a 實查新發現：顏色被當成語意選擇器（規格沒記，比色票分岔嚴重）

`skills/html-report-to-deck/scripts/rebuild_chip_chart.py` L57／L67：

```python
d["note"]   = next((t for a, _, t in head    if "#9CA3AF" in a), "")
d["footer"] = next((t for a, _, t in reversed(tail) if "#9CA3AF" in a), "")
```

它靠 **`#9CA3AF` 這個色值**辨認「哪一段文字是註記」。chart 側只要換掉那個灰，

⚠ 這比「兩套深藍」危險：深藍分岔只是看起來不一致，這個是功能會壞而且無聲。

12 處全部散落、0 個具名——它是兩側耦合最深的一個檔。

### 9.1b 🔴 行動空間完整掃描（2026-08-19 使用者補充設計，取代先前的「母體＝主題」解讀）

使用者原文的流程：

```text
資料分析 → 掃描所有可成立的行動方向 → 每個方向判斷「成立／不成立／證據不足」
        → 只輸出成立的專利行動
```

範例（候選池 6 項）：

| 行動方向 | 資料是否支持 | 結果 |
|---|---|---|
| 積極申請／布局 | ✓ | 輸出 |
| FTO／侵權風險調查 | ✓ | 輸出 |
| 迴避設計 | ✕ | 不輸出 |
| 專利收購／授權 | ? | 證據不足 |
| 持續監控競爭者 | ✓ | 輸出 |
| 防禦性布局 | ✕ | 不輸出 |

→ 自然得到 3 個行動。另一份資料支持 6 種就輸出 6 種，真的只有 1 種也允許。

🔴 **Verifier 檢查的不是「你有沒有寫 ≥4 個」，而是「所有候選方向你是不是都評估了」**：

- `covered = 8/8` → PASS（即使成立 2、否決 4、證據不足 2，最後只印 2 個行動）
- `covered = 1/8`（其餘 7 個連判斷都沒有）→ FAIL → Retry

**「固定 4 個行動」→「行動數量不限，但行動空間必須完整掃描」。**

⚠ 這個設計把**母體從「主題」換成「行動候選池」**，比我先前寫的「母體對帳保留」
更準確——主題數會變動、無法當固定基準，候選池是**固定且可窮舉**的，
`N/M` 才有意義。⚠ 它也真正解掉了矛盾：輸出可以只有 1 項（無數量下限），
但完整性仍被強制（候選池全掃），而且是集合比對、零語意判斷。

⚠ **FAIL → Retry 接得上既有機制**：`ai_report_deck_runner` 已有「check_content
未通過且 CLI 未修改 content.json → 停滯」的重試迴圈，不需新建。

#### 9.7d 🔴 「技術空白」改成「利基」（2026-08-19 使用者提議，採納）

原本 D「技術重組／跨域整合」需要「**空白**／相鄰技術出現連結」，因為兩項都缺
而整項不進池。使用者提議把「空白」換成「**利基**」——採納，而且理由不只是措辭：

| 用詞 | 主張的是什麼 | 我們的資料撐不撐得起 |
|---|---|---|
| 技術空白 | 「這裡**沒有人**做」＝缺席主張 | ❌ 母體只是**匯入的公開專利**。沒出現可能是沒人做、可能是檢索沒撈到、可能還沒公開。拿「沒看到」當「不存在」 |
| 利基 | 「這裡**有人做但很少**」＝在場主張 | ✅ 象限「低件數·少申請人」正是這個：`patent_count ≥ 1` 但量與家數都低 |

⚠ **但要再收一層**：資料只說「低密度」，說不出「有價值」。低密度也可能是
技術做不出來、或市場根本沒價值。所以沿用 `_qlabel` 的先例——
**現象用資料的話（低件數·少申請人），行動用查證動作（「評估」利基切入）**，
不寫成「這是個利基機會」那種結論。

⚠ #10 與 #8 觸發條件相同（同一象限）但用途不同：#8 是「去讀那幾件」，
#10 是「評估要不要投」。同一個現象觸發兩個不同層級的行動是合理的
——池子是**行動空間**不是分類，本來就允許重疊。

⚠ 這**不等於 D 回到池裡**：D 的「技術重組／跨域整合」還需要「相鄰技術連結」，
那項仍然缺（見 9.7a）。#10 是從 D 的前半獨立出來的一個新行動，不是 D 本身。

⚠ 7–9 **不是新發明**：`_qlabel` 現在就在回「（象限名, 後續行動）」兩元組，
四格各有一個建議動作。池子把它們納進來，而不是另立一套——否則就是第三份
各說各話的行動清單（§7a 剛修完同型問題）。

#### 9.7b 🔴 判定由**引擎**算，不是由 CLI 判（與專案核心原則一致）

9.7 表格右欄全部是確定性規則——那代表**引擎算得出來**，不需要 LLM 判斷。
這與 `.ai-rules/workflows.md` 的核心原則一致：
「引擎先產可信的結構化資料；AI 只**輔助**，不決定正式分類、不算正式統計」。

⚠ 這與使用者原本的框架（LLM 掃描 → Verifier 檢查 covered）不同，差別在
**誰做判定**。改由引擎判定的好處：確定性、可重現、零 token、
而且 `covered = M×K/M×K` **恆等成立**（引擎不會漏掃自己的迴圈），
Verifier 就不必去防 LLM 偷懶——那個風險從根上消失。

CLI 的工作改為：對引擎判成立的行動**寫判讀文字**（有自由度的部分）。

#### 9.7e 🔴 「交給機械就不會犯上世代的錯嗎」——不會，會犯**另一種**（使用者提問，2026-08-19）

**會。而且它就是形式鎖的同一族。**

規則寫死之後，**規則沒涵蓋的真實機會永遠不會出現，且不會有任何地方報錯**。
v5／v7／v9 的核心機制不是「鎖住格式」，是「用一條規則決定了什麼能存在」。
把判定交給引擎，等於把這個決定權從 LLM 移到規則——問題沒消失，只是換了位置。

兩種錯的差別在**可見度**，這才是改引擎判定的真正理由：

| | LLM 判定的錯 | 規則判定的錯 |
|---|---|---|
| 可重現 | ❌ 每次不同 | ✅ 每次一樣 |
| 找得到根因 | ❌ 散在生成過程 | ✅ 集中在一條規則 |
| 能被實測推翻 | ❌「這次剛好這樣」 | ✅ 拿反例跑一次就現形 |

**每次都一樣錯，是可以修的錯。** 但這只在有下面兩道護欄時才成立。

##### 9.7e-1 護欄一：規則是**地板不是天花板**（沿用本專案既有的候選模式）

公司正規化與主題候選都是這個模式：**AI／規則產候選，另一方可推翻但必須留痕**。

- [ ] 9.7e-1a 引擎算**候選判定**（確定性、全覆蓋、零遺漏）
- [ ] 9.7e-1b CLI 可**加**規則沒觸發但資料支持的行動 → **必須附證據錨點**
- [ ] 9.7e-1c CLI 可**否決**引擎判成立的行動 → **必須附理由**
- [ ] 9.7e-1d 兩種偏離都寫進掃描檔，**閘門不擋，但一定留痕**
      ⚠ 擋了就變回天花板；不留痕就等於沒發生過
- [ ] 9.7e-1e **偏離次數本身是規則品質的訊號**：同一條規則每次都被推翻，
      代表規則錯了。純規則設計沒有這個回饋迴路，這是它最大的盲點

### 9.8 🔴 CLI 的驗證原則與自驗機制（2026-08-19 使用者要求）

> 「應該要有一個驗證原則或機制讓 CLI 能遵守。」

9.7e-1 寫的「附證據錨點」「附理由」**對 CLI 是空的**——隨便寫都算有寫。
需要的是一條**它能拿來自我檢查**的判準，而不是一堆事後才擋的規則。

#### 9.8a 一條原則：**可反駁性**

> **每一句你寫的判斷，都要指得出「如果哪一個引擎欄位是別的值，這句話就不成立」。**

⚠ 這條原則不是新發明——它是本專案**已經證明有效**的那個機制的抽象化：
「發現欄逐字引用引擎字串」之所以守得住，正因為它的反駁條件是機械的
（字串不符即紅）。把同一個形狀推廣到所有判斷。

給 CLI 的操作句：
**不要說「規則錯了」，要說「規則沒看 `X` 欄位，而這個主題 `X = Y`」。**

#### 9.8b 三個可機械驗的形式

| CLI 要做的事 | 必須附上 | 閘門怎麼驗（零語意判斷） |
|---|---|---|
| 引用數據 | 逐字引擎字串 | 字串比對（§7 現行作法，已上線） |
| 寫判讀 | ≥1 個 `欄位=值` 引用 | 欄位在該主題的引擎輸出裡存在，且值逐字相符 |
| **加**行動（規則沒觸發） | `欄位=值` ＋ 指出規則沒看這個欄位 | 同上 |
| **否決**行動（規則觸發了） | `欄位=值` ＋ 指出規則看錯哪裡 | 同上 |

- [ ] 9.8b-1 引用格式定成單一形式（例如 `[status=成長]`），**唯一定義處**，
      三個場合共用——不要三種寫法
- [ ] 9.8b-2 閘門：引用的欄位必須在 `topic_facts`／掃描檔裡存在，值逐字相符
- [ ] 9.8b-3 Red：引用一個不存在的欄位 → 紅；引用存在的欄位但值寫錯 → 紅
- [ ] 9.8b-4 ⚠ 引用字串屬**內部語言**，渲染前要移除或轉成讀者語言
      （同 §9.6b：內部判定不外洩）

#### 9.8c 自驗迴圈：CLI 交稿前自己先跑一次

現況：CLI 寫完 → runner 跑 `check_content` → 紅了把 `gate_output` 打回去改。
**CLI 從來沒有在交稿前自己驗過。**

- [ ] 9.8c-1 撰稿提示明確要求：交稿前自行執行 `check_content.py`，紅了自己修
      ⚠ 開發側 SKILL.md L367 早就有這條指令，只是產品側沒要求 CLI 用
- [ ] 9.8c-2 ⚠ **不移除** runner 那道閘門——自驗是省往返，不是取代把關。
      「它說它驗過了」不是證據
- [ ] 9.8c-3 自驗與 runner 驗**必須是同一支腳本**，不得為了自驗另寫一份精簡版
      （兩份必然分岔，且分岔時 CLI 那份會比較鬆）

#### 9.8d ⚠ 這套原則自己先過三問（design §1.2）

| 問 | 判定 |
|---|---|
| ① 不看語意能否判定？ | **過**。欄位存在 ＋ 值逐字相符，純比對 |
| ② 滿足它的**唯一**途徑＝做對？ | **不過（同 9.5 的洞）** |
| ③ 偏差是多出來的還是缺席的？ | 引用造假＝多出來的（可見）；該寫沒寫＝缺席，靠引擎地板兜住 |

⚠ **第二問的洞**：CLI 可以引用一個**真實存在**的欄位值，而那個值跟它的主張
毫無關係。這套機制驗的是**形狀**，不是**推理**。

⚠ 但它比 9.5 的證據錨點多一層防護：因為引擎**已經算過一個判定**，
CLI 的偏離是「與某一條具名規則不同意」，這在**累積**上是可稽核的
——同一條規則反覆被同一種引用推翻，不是規則錯就是 CLI 在鑽同一個洞，
兩者都看得出來。⚠ 單次仍然守不住，這點必須明講，不得宣稱閘門擋得住亂寫。

- [ ] 9.8d-1 掃描檔保留每次的偏離紀錄（規則、引用、理由），
      讓「累積可稽核」成立而不只是說法

#### 9.9b 🔴 使用者的第二句推翻了我原本的修法

我在 9.7e-2b 寫「年份窗改為**依母體推導**」——**那個修法不成立**。

`workspace 會變`：同一個 workspace 多匯入一批專利，母體變、門檻跟著變，
於是**同一個主題可能從「成長」翻成「衰退」，而技術本身什麼都沒發生**。
`全庫也會變`：全庫是所有 workspace 的和，變得更頻繁。

**兩個候選基準都不穩。** 這不是選哪一個的問題，是「有沒有絕對基準」的問題
——沒有。

#### 9.9c 三分法：數字該固定還是該浮動，看它的**依據**不是看它的位置

| 類別 | 例子 | 該怎麼辦 |
|---|---|---|
| **制度事實** | 專利公開延遲約 18 個月、專利年限 20 年 | **固定**，但必須註明依據（可外部查證） |
| **母體相對** | 中位數、分位數、占比 | **per-run 推導**，且**必須把基準值一起輸出** |
| **從一份觀察抓的** | `0.70`（38/55）、`5`、`(2011,2019)` | 🔴 兩者皆非，**要改** |

⚠ 現行年份窗其實**混了兩種**：「排除最近兩年（資料截止效應）」是**制度事實**
（新案未公開），那部分是對的；錯的是把它的邊界寫成絕對年份 `2025`。
⚠ 拆開之後，年份窗應該是「**母體最新申請年往前推 N 年**」，
其中 N 有制度依據（公開延遲），而起點跟著資料走。

#### 9.9d 判定必須**帶著它的基準**，否則跨批次不可比

母體相對的判定不是技術的**屬性**，是「**相對於本批母體**」的位置。
現在的輸出（`status = 成長`）讀起來像屬性，這是誤導的來源。

- [ ] 9.6b-1 掃描結果放 content.json 的**非渲染鍵**（比照既有 `_說明`／`_pages說明`
      的慣例），閘門讀得到、版面畫不到。⚠ 不可放進任何會被 `slide_*` 取用的欄位
- [ ] 9.6b-2 洩漏閘門：`成立`／`不成立`／`證據不足`／`covered`／`N/M` 這類判定與
      對帳措辭，**不得出現在任何會被渲染的文字**（沿用 deepen 4.2 的有限黑名單
      作法，不做模式比對）
- [ ] 9.6b-3 Red：把「證據不足」寫進某頁 `lines` → 要紅
- [ ] 9.6b-4 反向驗證：黑名單清空 → 9.6b-3 要變綠（證明是黑名單在擋，
      不是別的規則順手擋掉的）

#### 9.6b-5 ⚠ 但「掃過」這件事必須留得下證據

掃了卻完全不顯示，使用者無從判斷掃得對不對——這是我原本寫 9.6.6 的理由，
理由仍然成立，只是**落點錯了**。修正後的分工：

| 給誰看 | 放哪 | 內容 |
|---|---|---|
| 閘門與稽核 | 工作目錄的掃描檔（非渲染） | 全部候選、判定、證據錨點、理由 |
| 報告讀者 | 投影片 | **只有成立的行動**，用結論語言 |

- [ ] 9.6b-6 掃描檔隨產出一併保存（比照 `topic_facts.json`／`cover_stats.json`），
      使用者要查「為什麼沒建議 X」時打得開
- [ ] 9.6b-7 ⚠ 若日後決定要在報告裡交代「哪些方向看過但沒建議」，
      **措辭必須另行設計**（讀者語言，例如「本次資料未支持」），
      不得直接搬內部判定值——這條先記著，本輪不做
- [ ] 9.6.7 Red：漏掉一個候選方向 → `covered 7/8` → 紅
- [ ] 9.6.8 Red：全部標 `證據不足` 但都沒寫「還缺什麼」→ 紅
      （驗 9.6.5 真的有牙齒，不是宣示）
- [ ] 9.6.9 反向驗證：把 `covered` 對帳字串改成硬編碼 `8/8` → 必須紅
      ⚠ 對帳數字若可由 CLI 自填而不被核對，這整套就只是裝飾

#### 9.5 這道閘門先過三問（design §1.2）

| 問 | 判定 |
|---|---|
| ① 不看語意能否判定？ | **過**。錨點在不在引擎輸出裡，是集合比對 |
| ② 滿足它的**唯一**途徑是否＝把事情做對？ | **不過（有洞，見下）** |
| ③ 偏差是多出來的還是缺席的？ | 錨點造假＝多出來的（可見）；但**整項不寫**＝缺席 |

⚠ **第二問的洞**：CLI 可以隨便挑一個**真的存在**的專利號填進 evidence 來過關
——錨點存在不等於它支持那個結論。這就是為什麼 9.5.4 明講不驗強度：
承認這個洞、把它留給人看，比假裝閘門守得住好。
⚠ 也正因為有這個洞，**9.1 第 3 點的證據鏈不能取代母體對帳**（見 9.1 解讀）：
對帳管缺席，是這道閘門結構上管不到的方向。

## 7. 版型庫收斂（2026-08-18 新增）

⚠ 全部零自由度——只驗「有沒有、幾個」，不驗好壞。適用情境那類有自由度的，
一律留在輪二。

### 7a. 三份清單各說各話（根因）

實查：能畫的（`deck_layout`）、會擋的（`check_content`）、CLI 照抄的
（`content-template.json`）互不一致。`conclusions` 有畫法、有閘門，
**範本裡沒有**——CLI 不宣告就 `if not cc: return []` 靜默放行，那頁根本不產出。

- [x] 7a.1 Red：版型清單唯一定義處 `deck_layout.LAYOUTS`（比照 `ACTION_VERBS`）
- [x] 7a.2 Red：**三處同步閘門**——`check_content` 認得的、範本示範的、
      `narrative.md` 寫到的，三者集合必須等於 `LAYOUTS`；任一缺漏即紅
- [x] 7a.3 反向驗證：`LAYOUTS` 加一個不在範本裡的版型 → 閘門要紅
      ⚠ 這條會**當場抓出還有哪些版型漏登記**，不要跳過
- [x] 7a.4 `conclusions` 補進 `content-template.json`

### 7b. 結論頁閘門的三個破口

現況 `_check_conclusions` 的三行：

```python
if not cc: return []      # ① 沒宣告就放行
if not rows: ...          # ② 只驗非空——10 主題寫 1 列全綠
if topic in facts: ...    # ③ 主題名不在 facts 就整個跳過逐字比對
```

- [x] 7b.1 Red：`conclusions` 缺席時要紅（頁是必要的，不是可選的）
- [x] 7b.2 Red：主題名不在 `topic_facts` 時要紅（不得靜默略過比對）
- [x] 7b.3 Red：**涵蓋率對帳**——`conclusions` 要帶 `covered N/M` 與
      未涵蓋主題的逐條原因；缺對帳即紅
      ⚠ **不是最小列數**。規定列數是形式鎖（v5／v7／v9 三次的同型錯），
      會逼出硬湊；涵蓋率只要求「沒寫的要現形」，偏差從缺席變成可見清單
- [x] 7b.4 反向驗證：把某主題從結論刪掉但不更新對帳 → 要紅

### 7c. 表格通用版型

表格繪製**已經會了**（`slide_conclusions` 的四欄表、`CONCL_COLS` 欄寬），
只是綁死在那一頁。

- [x] 7c.1 抽成 `layout: "table"`：**參數化欄數與欄寬**（2026-08-18 使用者裁決）
      欄寬由版型依欄數計算，總和不得超過可用寬（沿用 `CONCL_COLS` 的內距紀律）
- [x] 7c.2 Red：欄數與資料列的欄位數不符即紅；欄寬總和超寬即紅
- [x] 7c.3 `slide_conclusions` 改用通用表格版型，不留第二份畫法

### 7d. 路線圖頁併入結論頁

2026-08-18 使用者裁決：**期程欄整個拿掉**；路線圖頁與結論頁合併成一頁。

⚠ 期程（`短期 0–3 個月` 等）是全份唯一沒有資料支撐的欄位——系統不知道人力、
預算與產品排程，那個數字必然是編的。

- [x] 7d.1 移除 `content-template.json` 的 `roadmap*` 區塊與三期程
- [x] 7d.2 結論頁改為**依 `ACTION_VERBS` 分組**呈現（同一批 rows，換分組）
- [x] 7d.3 排序依**外部訊號**：該主題的他人審查中件數（多者在前）
      ⚠ 這是對手給的時間壓力，有資料可查證；不是我們假設的月份
- [x] 7d.4 Red：`roadmap` 仍出現在 content 即紅（避免舊範本殘留）

### 7f. 專利行動改為可多選（2026-08-19 使用者裁決，規格回寫）

使用者：「一種策略也許適用多個主題，也可能只適用一個主題……但也不是說行動就
只能選擇一種而已。」前半（一動詞對多主題）7d.2 的分組本來就成立；後半不成立
——`action` 是單一字串，等於強迫一主題一行動。「先迴避設計、同時追蹤對手審查
中的案」寫不出來就得二選一，而被丟掉的那個**不留任何痕跡**（缺席型偏差）。

- [x] 7f.1 `deck_layout.row_actions()`＝解析唯一定義處（字串／list 都收）；
      `check_content._bad_actions()` 讀同一份——多值最容易漏「只驗第一個」
- [x] 7f.2 該列在每個宣告動詞的分組下各出現一次；行動格印本分組動詞，
      其餘掛「同時：X」灰小字，避免讀者以為分組錯了
- [x] 7f.3 ⚠ **不加**「至多／至少 N 種」數量鎖（v5／v7／v9 形式鎖同型）。
      約束留在既有那條：每個動詞都要能從同列「判讀」推得出來
- [x] 7f.4 半真機械鏈實跑到多動詞列（`test_deck_runner_semireal` 代打 CLI）

### 7g. 兩個只有真產 pptx 才會炸的錯（半真鏈抓到，2026-08-19）

⚠ 兩個都是「同一份知識兩個落點」，而且**deck 側單元測試全綠**——
SVG 路徑與 PPTX 路徑對同一份輸入不同意，沒有人對帳。

- [x] 7g.1 `{"size": 11}` 裸 int：SVG 讀 pt 數值正常，PPTX 當成 11 EMU
      → 0 centipoints 直接 ValueError。修在 `_set_font`（唯一落點）。
      ⚠ 判斷用 `Length` 不是 `int`——`Pt(16)` 是 int 的子類別，第一版修法
      把既有 `B_SIZE` 二次換算，同一個 ValueError 換個數字
- [x] 7g.2 字級白名單兩份（`deck_layout` 定 24/16、`audit_deck` 寫死
      `"24,16"`）→ 收斂成 `ALLOWED_SIZES`，audit 預設讀它；
      新增 `S_SIZE = Pt(11)` 註記小字層級（不是「塞不下就縮字」的後門）
